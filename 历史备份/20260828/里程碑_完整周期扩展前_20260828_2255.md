# 2026-08-28 v0.12.7 统一入口、执行器业务通道与热修复收口

记录时间：2026-08-28 22:49 CST

## 里程碑结论

Xynigo 已从“云端页面 + 旧本机页面并存”推进到“云端 Web 统一入口 + 本地执行器安全执行”的共享测试阶段。`workspace.rpc.v1` 已把物流查询、买家号文件解析与入库、账号注册、HubStudio 建环境、店铺/代理读取和文件导出交给当前用户配对的本地执行器；PostgreSQL 保存任务、租约、进度与脱敏回执，本机敏感正文使用独立域 AES-GCM 后才进入任务存储。

这次切换不是一次干净的新版本发布，而是在两位采购同事真实电脑上连续暴露问题后形成的 `v0.12.7` 热修复列车。当前 Windows 已推进到 hotfix11，macOS 已推进到 hotfix7。功能已可供共享测试团队使用，但版本治理、平台签名、真实设备验收和主工作区收口尚未完成，不能称为生产上线。

## 已实现能力

1. 云端 Web 是员工统一业务入口；本机旧页面只保留诊断和回滚。
2. 设备使用 5 分钟一次性配对码，凭证进入 Keychain / CurrentUser DPAPI；云端设备接口同时按组织和当前用户隔离。
3. 本地执行器通过 20–25 秒 HTTPS 长轮询领取任务，使用租约、幂等键、进度与不确定态避免重复外部写入。
4. `workspace.rpc.v1` 只接受服务端白名单路径和方法；敏感买家号文件与结果单独加密。
5. Windows 标准安装包具备状态中心、托盘、协议启动、覆盖安装、构建修订运行时目录和在线更新基础。
6. macOS 标准包已带可信 CA 包，冻结运行时可以验证云端 TLS。
7. HubStudio Local API 使用有限端口、回环直连、认证状态和明确错误码；不把 `hubstudio-cli` 作为采购员依赖。
8. 状态中心定版 UI 已合入完整热修复主线：总体状态、云端/HubStudio/任务/版本四卡、动态配对区和原生托盘菜单。

## 关键踩坑经验

### 版本与安装包

- 同一 SemVer 下不断上传新资产会让标签、Release、云端目录和员工已安装运行时失去一一对应关系。`v0.12.7` 已证明这种做法难以审计；下一步必须提升版本号。
- NSIS 的根启动器覆盖成功，不代表版本目录中的 Python 执行器已更新。安装回归必须预置旧同版本运行时，再验证 `current-version`/构建修订真正切换。
- 在线更新涉及执行器、状态中心、安装器和新执行器四个生命周期，不能用“等待一个 PID 退出”作为成功条件。
- 未签名不是普通提示问题。Smart App Control 不支持单应用例外；内部测试可以人工关闭，团队稳定使用必须做 Authenticode/Developer ID。

### Windows 原生 UI

- Walk Declarative 的字符串图片由资源管理器相对可执行目录解析；绝对路径会被二次拼接。
- 原型必须承认 Win32/Walk 的真实边界。复杂圆角品牌菜单不会自动变成原生托盘菜单；先画可落地结构，再写代码。
- 后台诊断命令也会影响用户体验。任何 `tasklist`、Python 或辅助命令都要显式隐藏控制台并限制调用频率。

### 云端与本机通道

- “页面在线”“云端有设备”“本机能执行白名单业务”是三种不同状态，必须分别检查心跳、能力版本和 RPC 支持。
- 回环流量必须绕过系统代理；否则 localhost 可能被代理软件转发，形成难以识别的连接错误。
- 轮询不是越频繁越实时。空闲轮询也会生成任务、租约和数据库负担，必须防重入、合并读取并设置退避。
- 设备授权不能只按租户；共享电脑场景下还要按当前用户 owner 隔离。

### 数据与外部写入

- PostgreSQL 外键、事务 flush 和 SQLite 默认行为不同；测试库必须主动开启等价约束。
- Cookie 校验要验证安全属性与目标站点，不能把“结构不同”直接等同于无效；真实账号会包含多来源登录 Cookie。
- 外部任务失败后页面必须重新读取服务端状态，不得靠本地行快照猜测是否成功。
- 不确定结果不得自动重试。物流、建环境、买家号、飞书和采购外部写入都必须使用幂等键、接管和人工复核边界。
