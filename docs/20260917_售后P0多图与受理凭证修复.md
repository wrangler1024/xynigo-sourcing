# 售后 P0：多图与受理凭证

基线 `3b8c6e7`（v0.18.3）。用户授权修复两个功能缺陷；本记录描述开发候选，不代表发布或真实退款写入验收。

## 多图在提交后退化为单图

提交条目保留 `goodsImages`、`goodsItems`、`itemCount`；订单件数来自平台明确总数，不按图片数推算。批次请求摘要及结果表保存商品快照，结果、提交历史、重提及 Excel 保留同一份信息。旧单图字段兼容，历史记录未采集的件数保持未知。

完整商品数组只上传到云端批次一次，不随任务下发和每轮全量进度重复传送。提交前检查报文大小，超大明细提示分批，避免到写入后才发现进度超过限制。

## 受理凭证和操作完成时间

- 在本次点击前观察平台现有提交请求的响应，不另发或重放写请求。只处理同源退款创建接口，绑定订单、实际选择的包裹、理由和原路退回参数；成功还须 HTTP/业务成功以及匹配订单的成功退款单号，不能只看 `code=0`。
- 页面跳转依赖提示框关闭回调，不能把未跳转直接解释为未受理。已取得匹配提交响应时，即使页面未跳转，也可只读打开该退款详情读取平台阶段、掩码账户与退款渠道。
- 仅有跳转链接时，还需验证正文身份、目标包裹、退款理由、有效阶段和动作时间窗口。不得把同订单的另一个包裹凭证硬塞给当前包裹。
- 未取得直接响应时，只读核验本轮目标包裹是否已达到受理状态。来源为 `recovered_verified`，表示提交后核验目标已受理，不推断操作者或本次新增笔数。仅见历史、拒绝或其他包裹记录，仍不能完成当前目标。
- 所有结束路径都检查冻结目标包裹集合的凭证覆盖；资格列表清空不能代替缺失包裹的受理证据。明确凭证已覆盖全部目标后，后续只读查询失败只记诊断，不覆盖已受理结果。
- `submissionError` 保留原提交异常，`recoveryError` 保留补查异常。备注给出当前结果，详情展示执行诊断及真实平台阶段；不再统一写“无法确认由本次提交产生”。字段补齐后清除过时的缺失提示。
- `operationCompletedAt` 单独记录每单操作结束时间，并在重复回传中保持不变。它与平台申请时间、旧 `submittedAt` 分离；旧记录没有该字段时不拿接收时间或估算时间填充。

## 兼容与交付

迁移 `0042_after_sale_result_facts` 增加商品快照、操作完成时间及诊断列，旧行保持未知值。新执行器能力为 `after.sale.claim-evidence.v1`；先升级云端兼容接收方及迁移，再分发执行器。单独热更新 Web 不能修复采集与提交凭证。

退款跟踪、历史和导出仍可读取旧凭证。前端将本轮执行状态与平台退款阶段分开呈现；“已受理”计订单目标结果，不承诺退款到账或归因于某位操作者。未知写结果继续禁止直接补提。

验证使用合成请求/响应、临时数据库和本机隔离 PostgreSQL。真机只读验证既有退款详情的数据结构；业务证据留在私有记录中，未触发真实售后提交、历史回填或线上部署。
