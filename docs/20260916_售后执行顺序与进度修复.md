# 售后执行顺序与进度修复

状态：本地实现与回归验证完成，待独立评审；未推送、未合并、未部署、未发布执行器。
分支：`codex/after-sale-order-progress`；基线：`6952647`，包含此前所有订单扫描修复。

## 三项测试反馈

1. 提交和回访的执行顺序必须与列表从上到下一致。
2. 回访不能刚开始就按结果行数显示满进度。
3. 扫描完成后取消自动收起，保留手动收起/展开。

## 实现口径

- 扫描勾选按页面行序生成请求，忽略复选框点击先后；指定单按输入顺序，重提和历史回访按来源行序。
- 执行器仅合并相邻同环境条目；A/A/B/A 执行顺序仍为 A/A/B/A，不重排成 A/A/A/B。
  本地提交快照保留请求插入顺序；云端提交快照、历史详情与导出按请求摘要中的订单顺序排列。
- 当前页发起后立即列出全部等待行，后续结果按请求键回填原位置。回访显示等待、回访中、失败和停止状态。
- 回访复用已有 `executor_tasks.progress_summary` 保存该任务的结果行，无新表或迁移。
  尚未上报、queued、running 和 stopped 行不计入实际已处理数；失败行计入已处理，退款阶段不是执行进度。
  同一退款单在另一回访任务中的旧结果不能计入新任务进度。
- 新任务 GET 与导出均读取任务级行快照，按请求退款单顺序；部署前已结束且没有快照的旧任务，保留旧跟踪表回读兼容。
  未完整回传结果的结束任务显示“结果未齐”，不强行满格。
- Web 消费 `summary.progressCompleted/progressTotal`；旧云端缺少进度字段时保守显示 0，不使用历史结果行数推算。
  扫描进度分母明确按环境数，不被同环境多条订单行放大。
- 轮询不重入，丢弃已切换任务的迟到响应；扫描终态退出轮询，保留手动折叠状态。
  其他阶段既有自动折叠行为不在此次扫描反馈范围内。
