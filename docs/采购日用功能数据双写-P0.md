## 业务定位

当前团队共享的测试版中，“买家号建环境”和“查询物流单号”已是采购同事每日使用的实际工作流程，不再按纯合成测试数据处理。每次任务结束后应形成两份可追溯数据：

1. PostgreSQL 保存任务和明细事实，承担幂等、审计和后续下单绑号。
2. 飞书多维表保存采购协同镜像，便于日常查看和跟进，不承担事务裁决。

这一口径不代表整套 Xynigo 已转为正式生产系统；其他尚在辅助测试的功能继续保持原有测试边界。

## 数据链路

```text
本机任务完成
  → 先落本机持久化待发队列
  → 使用当前飞书登录会话 PUT 到云端
  → PostgreSQL 同一事务写入任务、结果和 operational_sync_outbox
  → 云端 Worker 按“同步键”写入/更新飞书记录
  → 写后回读成功才标记 completed
```

本机网络、登录会话或云端短时异常时，结果保留在本机待发队列并指数退避重试；云端已接收而飞书失败时，事实仍在 PostgreSQL，Worker 有限重试。两层均使用稳定任务键，重复上报不会重复建数据。

## 服务端接口与权限

| 方法与路径 | 用途 | 权限 |
|---|---|---|
| `PUT /v1/operations/environment-creation-runs` | 上报一次建环境任务及逐账号结果 | `resource.environment.create` |
| `PUT /v1/operations/logistics-query-runs` | 上报一次物流查询及逐环境结果 | `fulfillment.order.read` |

同一租户的 `runKey` 重复提交且内容完全一致时返回既有结果；内容不同时返回 `409 operation_run_idempotency_conflict`，不覆盖原事实。成功的建环境结果会同步补充无凭证的 `buyer_accounts` 安全资源账本，为后续下单绑定做准备；已有冲突绑定不会被静默覆盖。

## 安全边界

- 不写入密码、Cookie、接码 Key、App Secret、Access Token、Refresh Token 或完整账号。
- 账号只上报 SHA-256 安全引用和脱敏标签；错误只保留受限长度的单行脱敏摘要。
- 服务端契约使用 `extra=forbid`，凭证命名字段会被直接拒绝，不在错误或审计中回显。
- PostgreSQL 是事实源；飞书写入失败不回滚已确认的业务事实。
- 不为验收向真实协同表注入合成记录；首条记录应由采购同事的真实任务产生。
