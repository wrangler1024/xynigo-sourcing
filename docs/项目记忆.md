## 产品定位

Xynigo Sourcing 是面向跨境电商团队的采购协同与本地自动化系统。当前稳定能力运行在采购员电脑，通过本机 Web 页面调用 HubStudio Local API/CDP，并可通过企业自建应用读写飞书多维表格。

系统后续采用“云端控制面 + 本地执行器”形态。当前已有隔离的云端认证测试实例，并已完成真实飞书登录、一次性本地登录桥和本地开发版权限接入；云端尚未接管采购业务，成员审批、角色授权和会话管理页面仍未完成。

## 已完成的前端决策

- 沿用 Xynigo 现有品牌、色彩、侧边栏和 Banner 视觉语言，不重新设计一套 UI。
- 一级和二级导航统一位于左侧边栏；一级菜单选中态不使用多层叠加效果。
- 二级业务页采用工作区多 Tab：最多同时打开 10 个，溢出时可横向滚动，并提供页签清单、关闭其他和关闭右侧。
- “规划”入口与“现有”入口必须明确区分；规划页不得使用伪造演示数据冒充已实现能力。
- 本轮验收范围是桌面端。移动端短期不开发，不作为本里程碑完成条件。
- `file://` 只能查看静态页面；完整运行必须使用启动窗口显示的 `http://127.0.0.1:<port>/` 地址。
- 登录后的账号入口位于顶部状态区最右侧；窄屏只显示头像，姓名、角色和退出统一放入下拉菜单。飞书头像与姓名缩写只能二选一显示。

## 当前后端事实

- 本地入口为 `purchase_tool.main`，使用绑定在 `127.0.0.1` 的 `ThreadingHTTPServer`。
- `main.py` 同时承担 HTTP 路由、进程级状态和任务编排装配，尚未拆分为版本化 API 层。
- 真实业务能力主要位于：
  - `shein_query.py`：订单和物流查询；
  - `buyer_library.py`：买家号库读取与号商账号入库；
  - `buyer_register.py`：买家号注册流程；
  - `env_batch.py`：采购/备用环境创建与出口 IP 验证；
  - `hub_api.py`、`cdp.py`：HubStudio Local API 和浏览器执行；
  - `lark_openapi.py`、`lark_ledger.py`：飞书 OpenAPI 与统一台账写回。
- 本地服务仍只绑定回环地址，但已经通过云端会话摘要执行登录门禁和主要业务 API 权限校验；浏览器 POST 接口同时校验同源。它仍不是可直接暴露公网的版本化公共 API。
- 已在 `cloud/auth-service/` 建立独立的云端认证服务。服务包含飞书 OAuth v3、一次性 state、受控 PKCE 兼容开关、待审批用户、显式超级管理员、RBAC、摘要会话、一次性本地登录桥和审计模型。
- 云端迁移当前包含 `0001_identity_foundation` 和 `0002_local_login_bridge`。业务表为 `tenants`、`users`、`roles`、`permissions`、`user_roles`、`role_permissions`、`sessions`、`oauth_login_attempts`、`audit_events`、`local_login_requests` 共 10 张；加 `alembic_version`，public schema 共 11 张表。
- 认证测试入口为 `https://xynigo.samforo.icu`；Nginx 终止 HTTPS，认证容器只绑定服务器 `127.0.0.1:8080`，PostgreSQL 不发布宿主机端口。测试部署未改变本地采购服务、HubStudio 或现有 n8n 服务。
- “小犀代采”应用已登记精确回调 URL `https://xynigo.samforo.icu/v1/auth/feishu/callback`，并完成真实超级管理员登录、权限摘要、会话落库、本地页面登录和退出验证。
- 飞书对当前应用的 PKCE challenge 仍返回 `20049`；测试实例暂时关闭 PKCE challenge，但继续保留随机 state、五分钟有效期、摘要存储和单次消费。代码默认值仍为 S256，飞书侧兼容后应恢复。
- 本地云端会话由 Python 服务通过一次性轮询桥换取，macOS 保存到 Keychain、Windows 保存到 CurrentUser DPAPI；前端网页不接触轮询令牌或最终会话令牌。
- 后台任务状态主要保存在进程内存；进程退出后不具备统一的云端任务恢复和审计能力。
- 飞书买家号库列表只返回脱敏字段；号商入库采用“本地解析 → 飞书只读查重 → 脱敏预览 → 单独确认写入”。
- 新建环境的出口 IP 验证使用 HubStudio 无头后台浏览器验证全部新建环境，不打开真实可见 Hub 窗口。

## 目标架构决策

目标链路如下，状态为“云端认证与本地登录闭环已在测试环境验证；成员权限管理、设备通道、业务控制面和生产切换尚未完成”：

```text
飞书登录 / 外部业务服务
          ↕ HTTPS
   Xynigo 云端控制面
          ↕ 本地主动轮询（首期）/ WebSocket（后续）
   Xynigo 本地执行器
          ↕
HubStudio Local API / CDP
```

边界原则：

- 云端控制面负责身份、组织、权限、业务任务、分发、审计和外部服务集成。
- 本地执行器负责只有本机才能完成的 HubStudio/CDP 操作，不开放公网入站端口。
- 首期优先使用本地主动 HTTPS 轮询，待实时性和规模确有需要再增加 WebSocket。
- 飞书登录用于识别系统用户；企业自建应用凭证用于服务访问多维表格，两者是不同的鉴权域，不能混用。
- 前端只能通过 Xynigo 后端访问飞书，不直接持有飞书应用密钥或调用敏感写接口。
- 多用户并发后，交易状态和账号分配锁不能只依赖飞书表或单进程锁。云端数据库应成为工作流与权限的事实源，飞书作为协同视图和外部业务账本同步。
- 腾讯轻量服务器可承载首期单节点控制面，但正式开放前必须具备 HTTPS、备份、最小端口暴露、日志脱敏、凭证托管和恢复演练。
- 当前测试实例已完成 HTTPS、最小端口暴露、root-only 数据库备份、恢复演练、重启持久化和真实登录验证；正式开放前剩余重点是普通成员审批/角色联调、会话撤销管理、异机备份、告警和绿色包灰度。

### 登录与成员准入决策

- 飞书应用可用范围只决定成员能否发起授权，不等于自动获得 Xynigo 访问权。
- OAuth 返回的企业租户必须命中云端 `tenant_key` 白名单；其他企业直接拒绝。
- 未知企业成员首次授权只创建 `pending` 用户，不签发会话；自动激活默认关闭。
- 只有明确配置的超级管理员可在首次登录时激活并初始化系统角色。普通成员必须由管理员批准并分配角色后才能进入业务模块。
- `active`、`pending`、`disabled` 是云端权限事实；成员停用必须同时支持撤销其有效会话。
- 当前只有超级管理员真实闭环，成员审批、角色分配、会话管理 API 和页面是下一阶段最高优先级。

### 首期客户端与启动体验决策

- 云端 Web 工作台是唯一的用户界面；不开发 Electron、Tauri 等桌面壳，也不在桌面应用窗口中嵌入云端网页。
- 本地仅保留极简、无业务界面的 Xynigo 执行器，负责主动连接云端并调用 HubStudio Local API/CDP。云端网页独立运行：执行器退出后仍可登录和查看云端数据，但本机显示离线，依赖 HubStudio 的操作不可执行。
- 首期不强制开机自启动。用户操作流程固定为：手动启动并登录 HubStudio → 手动启动 Xynigo 执行器 → 在云端 Web 工作台登录 Xynigo → 执行业务任务。
- 首期执行器只检查 HubStudio Local API 是否可用并上报明确状态；HubStudio 不可用时只提示用户处理，不负责自动启动、自动登录或自动修复。
- “执行器检测并自动拉起 HubStudio、复用已登录实例、自动定位 macOS/Windows 安装路径”属于后续体验优化，不进入首期核心业务范围。
- 首期优先开发云端鉴权与权限、设备连接、任务调度、采购业务流程及执行结果闭环；桌面壳、强制自启动和 HubStudio 自动拉起不得阻塞这些核心模块。

### 登录后检测与拉起 Xynigo（后续优先优化）

- 飞书登录成功后，云端 Web 工作台通过云端保存的设备心跳判断本机 Xynigo 执行器是否在线，不把网页直接请求 `localhost` 作为主要检测方式，避免浏览器本地网络权限、CORS 和跨浏览器兼容问题。
- 执行器在线时直接显示“本机已就绪”；离线时显示明确的“启动 Xynigo”按钮。用户点击后，通过安装阶段注册的 `xynigo://` 自定义协议尝试拉起已安装的执行器，网页继续轮询云端设备状态确认是否启动成功。
- 在合理等待时间内没有收到执行器心跳时，网页显示“未检测到 Xynigo”，并按 macOS/Windows 提供对应安装包和人工确认安装指引。普通网页不得尝试静默安装本机程序，也不能把“用户拒绝拉起”和“尚未安装”误判为确定结论。
- 自定义协议只允许启动、唤醒和设备配对等低风险动作；参数必须使用一次性、短时有效票据，不能传长期凭证，也不能仅凭协议参数直接执行采购、写入或删除操作。
- 该能力不需要桌面壳，是极简执行器安装包、协议注册和云端设备状态页的配套能力。首期核心业务完成后，一旦进入“登录后衔接本地执行器”的体验优化，应优先实现本方案；其优先级高于自动拉起或自动登录 HubStudio。

### 采购业务数据与飞书多维表格演进决策

- 后续将 PostgreSQL 作为采购订单、订单明细、状态流转、支付/退款、物流、异常、任务结果和审计记录的唯一事实源；飞书多维表格逐步从业务主数据保存表调整为协同查看、人工处理和报表视图。
- 标准写入顺序是：业务操作先在 PostgreSQL 事务中落库并记录待同步事件，事务成功后再由异步任务同步到飞书。不得把“PostgreSQL 与飞书同时写成功”作为一个无法可靠保证的跨系统事务。
- 每次飞书同步必须有幂等键、外部记录 ID、同步状态、最后同步时间、失败原因和有限重试；写入后继续遵守回读确认，不确定结果不能标记成功，超过重试边界进入人工复核。
- 飞书默认不是任意字段都可反向修改主库。如确需在飞书人工处理，只开放预先定义的可编辑字段，并通过显式同步规则、版本校验和冲突状态回写 PostgreSQL，避免形成两个互相覆盖的主数据源。
- 该方向属于后期数据架构优化，不立即改变当前飞书统一台账及现有业务流程。迁移必须经过字段映射、历史数据导入、双边对账、灰度切换和回滚验证，不能一次性停用现有飞书表。
- 图片、发票和采购凭证等大文件后续放对象存储，PostgreSQL 只保存元数据和访问引用；密码、Cookie、App Secret 和访问令牌不得进入采购订单普通字段。

## 买家号与环境创建业务记忆

目标流程是“买家号先入库，再创建采购环境”：

1. 号商账号或未来自注册账号先进入买家号库。
2. 创建采购环境时只配置站点、环境数量、采购员分配等业务参数。
3. 后端从符合条件的可用买家号中分配并预占账号。
4. 本地执行器创建 HubStudio 环境、绑定账号/Cookie，并后台无头验证全部出口 IP。
5. 成功后写回绑定环境、采购员、状态和验证结果；失败时释放未使用预占，结果不确定时进入人工复核。

目前“买家号先入库”及现有环境创建已具备，但“按数量自动抽取、并发预占、超时释放”尚未实现，是资源中心后端的下一条核心业务链路。

## 不可破坏的安全约束

- 真实密码、Cookie、App Secret、访问令牌、代理链接和完整业务数据不得进入仓库、测试夹具、日志或截图。
- 所有真实平台写入必须保留明确确认；HubStudio 写入与飞书写入分别确认。
- 飞书写入必须先做字段/冲突预检，并在写后回读确认；不确定结果不能记为成功。
- API 错误和进度信息必须脱敏；公开配置接口不得回显 Secret、完整飞书链接、Base Token 或 Table ID。
- 后端权限必须作为最终裁决，隐藏前端菜单不能替代接口鉴权。
- 非超级管理员不得读取或修改飞书企业应用凭证和模块连接配置；权限接入后，前端隐藏“飞书连接”，后端配置接口同时返回 403。
- 任务下发必须有幂等键、租约/超时、重试边界和审计记录，避免重复创建环境或重复写账。
