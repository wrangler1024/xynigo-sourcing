## 产品定位

Xynigo Sourcing 是面向跨境电商团队的采购协同与本地自动化系统。共享测试环境已经以 `https://xynigo.samforo.icu` 提供云端 Web 工作台，身份、权限、采购协同、买家号安全摘要和审计直接访问云端；员工电脑不启动本地服务也能进入工作台。本地执行器继续负责 HubStudio Local API/CDP、SHEIN 浏览器和其他只能在采购电脑完成的动作。云端与本机必须复用 `src/purchase_tool/web/index.html` 这一份前端源，不为云端另做视觉、导航或页面分支；运行环境差异只通过 API 适配和状态提示表达。浏览器地址栏/标签页统一使用 `xynigo-x.ico`，云端 `/favicon.ico` 只是该文件的同内容别名，不使用犀牛吉祥物图。

系统后续采用“云端控制面 + 本地执行器”形态。当前已有隔离的云端测试实例，并已完成真实飞书登录、一次性本地登录桥、成员/角色/权限/会话管理、运营采购单基础，以及买家号/建环境/物流结果的 PostgreSQL + 飞书 Outbox Worker。新刚、志恒已完成新增/审批、角色分配和真实电脑登录；最小权限采购员角色、停用与会话撤销、真实下单执行及生产发布仍待完成。

云端 Web 的本地执行器入口固定为“双入口、同一页面”：顶部栏是全局连接状态入口，“系统管理 → 本地执行器”是下载安装、启动引导、配对、设备管理和本机配置的固定页面。首次安装不得复用已安装执行器的“检查更新”按钮。下载清单必须由云端提供并绑定当前应用版本及不可变发布标签，至少包含平台、架构、文件名、大小和 SHA-256；浏览器只能在用户明确点击后下载，不能静默安装、运行或绕过系统安全提示。下载完成、安装完成、本机启动和云端在线是四个不同事实，只有云端收到设备凭证认证的最新心跳后才能显示在线；Web 直连 `localhost` 不作为主通信路径。

云端下载目录必须长期保留绿色版兜底。平台推荐资产可以是标准安装包，并通过同版本 `greenFallback` 绑定绿色包；标准包不存在、下载地址不可用或签名门禁未通过时，Web 自动切换绿色包，显示真实文件名、大小、SHA-256 和对应启动方式。新版 Windows 绿色包根目录固定包含 `Xynigo.exe` 品牌状态中心、托盘、品牌资源和自包含运行时，兼容 `启动.bat`、旧本机界面及人工配对脚本；绿色版不注册 `xynigo://`，必须由用户完整解压并明确启动。SHA-256 只能证明文件完整性，不能冒充发布者签名。带开发构建标签的绿色包不得上传或覆盖不可变 Release。

本地执行器 P1 的长期边界固定为：本机只主动建立 HTTPS 443 出站连接，首期使用 20–25 秒长轮询；用户会话与设备会话严格分离，设备接口拒绝 Cookie；配对码短时、一次性，设备凭证只进入 Keychain/CurrentUser DPAPI，数据库只存摘要。云端保存设备、任务、租约、短期脱敏结果和事件，不取代本机 `config.json`。配置写入必须带 expected revision、经过本地任务闸门并原子替换；已开始的写操作断线后保守标记为不确定，不能自动重放。代理链接、密码、Cookie、Token、飞书凭证及租约令牌不得写入普通状态文件、任务日志或审计。

Xynigo 的容量与扩展口径固定为：团队内部使用、现阶段不超过 50 人/50 台活跃执行设备，当前以单套无状态云端 API、PostgreSQL 任务事实源和 20–25 秒 HTTPS 长轮询为默认架构，不提前引入 Redis、Kafka、专用消息队列或复杂连接网关。通信协议必须与传输解耦；未来需要亚秒级通知时先增加 WebSocket `task_available` 通知，设备仍通过 HTTPS 领取、续租和回执，长轮询永久保留为降级。只有云端多实例后才使用 Redis Pub/Sub 做跨实例连接通知；只有事件吞吐、长期留存、顺序消费和多消费者需求经指标确认后才评估持久消息平台。任何新传输层都不能取代 PostgreSQL 任务事实、租约、幂等、审计和外部副作用人工接管边界。

标准安装包的配对操作固定为：云端创建一次性配对码时返回只用于状态查询的 `pairingRequestId`，Web 通过 `xynigo://pair?code=...` 唤起本机应用，再按请求 ID 查询 `pending / consumed / expired`，不能用设备列表中新出现的同平台设备猜测结果。`consumed` 只表示设备身份创建完成，服务端不得在配对接口伪造 `last_seen_at`；设备必须使用一次性返回并已进入 Keychain/CurrentUser DPAPI 的凭证完成首次长轮询后，才能显示在线。URL 只允许短时配对码，设备凭证和业务任务永不进入协议链接。

## 当前后端事实

- 本地入口为 `purchase_tool.main`，使用绑定在 `127.0.0.1` 的 `ThreadingHTTPServer`。
- `main.py` 同时承担 HTTP 路由、进程级状态和任务编排装配，尚未拆分为版本化 API 层。
- 真实业务能力主要位于：
  - `shein_query.py`：订单和物流查询；
  - `buyer_library.py`：买家号库读取与号商账号入库；
  - `buyer_register.py`：买家号注册流程；
  - `env_batch.py`：采购/备用环境创建与出口 IP 验证；
  - `resource_center.py`：店铺/环境只读对账、代理资产脱敏与本机健康检测；
  - `hub_api.py`、`cdp.py`：HubStudio Local API 和浏览器执行；
  - `lark_openapi.py`、`lark_ledger.py`：飞书 OpenAPI 与统一台账写回。
- 本地服务仍只绑定回环地址，但已经通过云端会话摘要执行登录门禁和主要业务 API 权限校验；浏览器 POST 接口同时校验同源。它仍不是可直接暴露公网的版本化公共 API。
- 已在 `cloud/auth-service/` 建立独立的云端认证服务。服务包含飞书 OAuth v3、一次性 state、受控 PKCE 兼容开关、待审批用户、显式超级管理员、RBAC、摘要会话、一次性本地登录桥和审计模型。
- 已部署租户隔离的成员审批/停用/恢复、按飞书绑定手机号精确解析并新增待审批成员、自定义角色生命周期、角色权限配置、成员角色分配、有效会话摘要与撤销 API；运营采购单基础随后通过 `0003_purchase_request_foundation` 部署。手机号只在请求期间发往飞书，不写入 Xynigo 数据库、响应或审计；管理变更写审计，停用成员同步撤销有效会话。
- 云端已固定维护 `super_admin`、`admin` 与默认无权限的 `member` 三个系统角色。当前 29 项权限目录下，`super_admin` 为 29/29，`admin` 为 26/29，并固定排除 `system.lark_connection.manage`、`system.integration.manage` 和 `resource.ip.credential.manage`。`super_admin` 与 `admin` 权限集由后端锁定，系统角色不可改名/删除；高敏权限不能授给其他角色，非超级管理员也不能分配超级管理员角色。
- 云端测试环境迁移为 `0012_buyer_account_credentials`，`0005/0007/0008/0009/0010/0011/0012` 已部署；其中包含业务/系统日志、采购下单闭环、买家号数据库事实源、完整凭证加密和买家号/建环境/物流飞书 Outbox。生产环境仍未部署。
- 认证测试入口为 `https://xynigo.samforo.icu`；Nginx 终止 HTTPS，认证容器只绑定服务器 `127.0.0.1:8080`，PostgreSQL 不发布宿主机端口。测试部署未改变本地采购服务、HubStudio 或现有 n8n 服务。
- “小犀代采”应用已登记精确回调 URL `https://xynigo.samforo.icu/v1/auth/feishu/callback`，并完成真实超级管理员登录、权限摘要、会话落库、本地页面登录和退出验证；新刚、志恒随后也在各自电脑完成 v0.11.1 飞书授权与工作台登录。
- 飞书对当前应用的 PKCE challenge 仍返回 `20049`；测试实例暂时关闭 PKCE challenge，但继续保留随机 state、五分钟有效期、摘要存储和单次消费。代码默认值仍为 S256，飞书侧兼容后应恢复。
- 本地云端会话由 Python 服务通过一次性轮询桥换取，macOS 保存到 Keychain、Windows 保存到 CurrentUser DPAPI；前端网页不接触轮询令牌或最终会话令牌。
- 本地 Python 服务已增加 `/api/admin/*` 安全代理；“组织与权限”二级入口下的成员管理、角色管理、权限策略，以及独立的登录会话页面只渲染云端返回的真实摘要，浏览器继续不接触云端 Bearer 会话。数据范围仅保留禁用规划入口，不接假数据或占位 API。

- 生产环境仍保持独立且未上线。采购同事使用测试环境不等于生产开放，测试账号、Cookie、数据库和飞书测试数据不得迁移到生产。

## 目标架构决策

目标链路如下，状态为“云端认证、本地登录和成员权限管理已部署到测试环境；超级管理员及两名真实成员已完成登录，最小权限/停用撤权收口、设备通道、业务控制面和生产切换尚未完成”：

```text
飞书登录 / 外部业务服务
          ↕ HTTPS
   Xynigo 云端控制面
          ↕ 本地主动轮询（首期）/ WebSocket（后续）
   Xynigo 本地执行器
          ↕
HubStudio Local API / CDP
```

边界原则：

- 云端控制面负责身份、组织、权限、业务任务、分发、审计和外部服务集成。
- 本地执行器负责只有本机才能完成的 HubStudio/CDP 操作，不开放公网入站端口。
- 首期优先使用本地主动 HTTPS 轮询，待实时性和规模确有需要再增加 WebSocket。
- 飞书登录用于识别系统用户；企业自建应用凭证用于服务访问多维表格，两者是不同的鉴权域，不能混用。
- 前端只能通过 Xynigo 后端访问飞书，不直接持有飞书应用密钥或调用敏感写接口。
- 多用户并发后，交易状态和账号分配锁不能只依赖飞书表或单进程锁。云端数据库应成为工作流与权限的事实源，飞书作为协同视图和外部业务账本同步。
- 2026-08-25 已废止“同一台广州轻量服务器同时部署测试和生产”的方案。共享测试服务器 `shared-test-gz-01` 只承载 `/opt/xynigo-auth-test` 测试环境；生产只能在独立实例 `xynigo-prod-gz-01` 的 `/opt/xynigo-auth-prod` 以 Compose 项目 `xynigo-auth-prod` 部署，域名为 `app.xynigo.com`。
- 测试与生产必须隔离 Docker 项目、网络、数据库、数据卷、数据库账号、`.env`、会话密钥、Cookie、日志、备份、飞书 Base/Table 和同步状态；生产库从空库执行批准的 Alembic 迁移，不复制测试数据库、数据卷或测试数据。
- 两个环境可以共用飞书应用“小犀代采”，但必须同时保留测试回调和生产回调，且应用共用不能成为业务数据或会话的共享边界。
- 生产正式开放前必须具备 HTTPS、仅 `80/443` 的公网边界、受限来源 SSH、备份与异机加密副本、日志脱敏、凭证托管、恢复演练、监控告警和一至两名采购员灰度。
- 当前测试实例已完成 HTTPS、root-only 数据库备份、恢复演练、重启持久化和真实登录验证。2026-08-25 用户确认 n8n 只是历史测试服务且未实际使用，已停止 `n8n` 容器并将重启策略由 `always` 改为 `no`；`n8n_n8n_data` 数据卷和容器仍保留，`5678` 已无监听，但云防火墙放行规则尚未删除。宝塔、FinePack Hub 和其他既有服务继续运行，未经明确授权不得停止或修改。
- 2026-08-25 最新只读复核：生产服务器 `xynigo-prod-gz-01` 已将 SSH 限制为管理员来源 `113.80.4.17/32`，公网规则仅保留 `80/443`、受限 SSH 和 ICMP；独立生产密钥权限为 `0600` 且实际登录成功。主机为 Ubuntu 24.04.4、2 vCPU/7.5 GiB/约 79 GiB，当前仅 SSH 监听，无 Docker、Nginx、数据库、生产目录或业务数据。主机层 UFW 仍未启用，SSH 密码认证与 root 登录仍允许；生产部署继续被主机加固、未批准 Git 提交、备案/DNS/TLS、生产数据路由、异机备份与监控等闸门阻断。完整记录见 [`架构决策-20260825-广州腾讯轻量服务器测试与生产双环境隔离.md`](架构决策-20260825-广州腾讯轻量服务器测试与生产双环境隔离.md)。

### 登录与成员准入决策

- 飞书应用可用范围只决定成员能否发起授权，不等于自动获得 Xynigo 访问权。
- OAuth 返回的企业租户必须命中云端 `tenant_key` 白名单；其他企业直接拒绝。
- 未知企业成员首次授权只创建 `pending` 用户，不签发会话；自动激活默认关闭。
- 只有明确配置的超级管理员可在首次登录时激活并初始化系统角色。普通成员必须由管理员批准并分配角色后才能进入业务模块。
- `active`、`pending`、`disabled` 是云端权限事实；成员停用必须同时支持撤销其有效会话。
- 新刚、志恒已完成手机号新增、管理员批准、角色分配和 v0.11.1 真实登录，成员准入与登录子闭环已完成。当前用于验收的是内置管理员角色；下一优先级是创建最小权限采购员角色并完成降权、停用、会话撤销、重新登录拒绝与跨租户边界验证。

### 首期客户端与启动体验决策

- 云端 Web 工作台是唯一的用户界面；共享测试入口已在 `https://xynigo.samforo.icu/` 落地。它必须保持部署前原版工作台的 UI，并与本机运行模式共用同一个前端源，通过同步脚本进入云端认证服务，禁止复制后独立改版。不开发 Electron、Tauri 等桌面壳，也不在桌面应用窗口中嵌入云端网页。
- 本地仅保留极简、无业务界面的 Xynigo 执行器，负责主动连接云端并调用 HubStudio Local API/CDP。Windows 标准版允许提供只展示连接、配对、版本、HubStudio 和本机任务状态的原生状态中心与托盘菜单，但不得在本机状态中心复制采购业务页面或绕过云端权限执行采购动作。云端网页已可独立运行：执行器退出后仍可登录、查看采购/资源/日志和执行云端认领，本机显示离线，依赖 HubStudio 的操作不可执行。
- 首期不强制开机自启动。用户操作流程固定为：手动启动并登录 HubStudio → 手动启动 Xynigo 执行器 → 在云端 Web 工作台登录 Xynigo → 执行业务任务。
- 首期执行器只检查 HubStudio Local API 是否可用并上报明确状态；HubStudio 不可用时只提示用户处理，不负责自动启动、自动登录或自动修复。
- “执行器检测并自动拉起 HubStudio、复用已登录实例、自动定位 macOS/Windows 安装路径”属于后续体验优化，不进入首期核心业务范围。
- 首期优先开发云端鉴权与权限、设备连接、任务调度、采购业务流程及执行结果闭环；桌面壳、强制自启动和 HubStudio 自动拉起不得阻塞这些核心模块。

### 登录后检测与拉起 Xynigo（后续优先优化）

- 飞书登录成功后，云端 Web 工作台通过云端保存的设备心跳判断本机 Xynigo 执行器是否在线，不把网页直接请求 `localhost` 作为主要检测方式，避免浏览器本地网络权限、CORS 和跨浏览器兼容问题。
- 执行器在线时直接显示“本机已就绪”；离线时显示明确的“启动 Xynigo”按钮。用户点击后，通过安装阶段注册的 `xynigo://` 自定义协议尝试拉起已安装的执行器，网页继续轮询云端设备状态确认是否启动成功。
- 在合理等待时间内没有收到执行器心跳时，网页显示“未检测到 Xynigo”，并按 macOS/Windows 提供对应安装包和人工确认安装指引。普通网页不得尝试静默安装本机程序，也不能把“用户拒绝拉起”和“尚未安装”误判为确定结论。
- 自定义协议只允许启动、唤醒和设备配对等低风险动作；参数必须使用一次性、短时有效票据，不能传长期凭证，也不能仅凭协议参数直接执行采购、写入或删除操作。
- 该能力不需要桌面壳，是极简执行器安装包、协议注册和云端设备状态页的配套能力。首期核心业务完成后，一旦进入“登录后衔接本地执行器”的体验优化，应优先实现本方案；其优先级高于自动拉起或自动登录 HubStudio。
- Windows 标准安装固定采用当前用户安装：默认进入 `%LOCALAPPDATA%\Programs\Xynigo Sourcing`，不请求管理员权限、不安装系统服务、不强制开机启动。开始菜单提供启动、配对和卸载，桌面快捷方式只能作为用户可选项。
- 标准安装的应用版本与用户数据必须分目录：`versions/<version>` 不可变，`config.json`、日志、运行数据和导入文件留在安装根目录。升级先落新版本再切换标记；卸载只删除应用与注册信息并保留用户数据。绿色包迁移只允许显式目录和数据白名单，不能扫描整机或复制旧代码/运行时。
- Windows `xynigo://` 首期只允许 `start`、`wake` 和五分钟一次性 `pair`；协议处理器拒绝长期凭证、重复/未知参数和任何采购业务动作。协议只是启动入口，最终在线仍由云端设备心跳裁决。
- Windows 标准安装包固定使用 Xynigo 品牌向导、图形化绿色包迁移页、原生状态中心和托盘菜单；状态中心只允许显示本机安全状态以及打开云端、配对、重启、日志和退出等低风险动作。它在可信 Authenticode 签名与 RFC 3161 时间戳、Windows 安装/升级/卸载 CI、新版本号和采购电脑实测完成前必须标记不可发布；不得用同一个版本号替换既有绿色包或 Release 资产。
- macOS 标准安装包采用原生 `.app + .pkg`，应用固定在 `/Applications`，用户数据固定在 `~/Library/Application Support/XynigoSourcing`；升级/删除应用不得连带删除用户数据。首发只维护 Apple Silicon，应用只做执行器启动和低风险协议入口，不建设第二套业务 UI，不注册强制自启动。发布前必须完成 Developer ID Application/Installer 双签名、Apple 公证与 stapling、Gatekeeper 离线验证、真实采购 Mac 安装/升级/迁移和新版本号；当前 ad-hoc/未签名开发包必须保持 `releaseEligible=false`。

### 采购业务数据与飞书多维表格演进决策

- 后续将 PostgreSQL 作为采购订单、订单明细、状态流转、支付/退款、物流、异常、任务结果和审计记录的唯一事实源；飞书多维表格逐步从业务主数据保存表调整为协同查看、人工处理和报表视图。
- 标准写入顺序是：业务操作先在 PostgreSQL 事务中落库并记录待同步事件，事务成功后再由异步任务同步到飞书。不得把“PostgreSQL 与飞书同时写成功”作为一个无法可靠保证的跨系统事务。
- 每次飞书同步必须有幂等键、外部记录 ID、同步状态、最后同步时间、失败原因和有限重试；写入后继续遵守回读确认，不确定结果不能标记成功，超过重试边界进入人工复核。
- 飞书默认不是任意字段都可反向修改主库。如确需在飞书人工处理，只开放预先定义的可编辑字段，并通过显式同步规则、版本校验和冲突状态回写 PostgreSQL，避免形成两个互相覆盖的主数据源。
- 该方向属于后期数据架构优化，不立即改变当前飞书统一台账及现有业务流程。迁移必须经过字段映射、历史数据导入、双边对账、灰度切换和回滚验证，不能一次性停用现有飞书表。
- 图片、发票和采购凭证等大文件后续放对象存储，PostgreSQL 只保存元数据和访问引用；密码、Cookie、App Secret 和访问令牌不得进入采购订单普通字段。

## 采购任务、下单分批与 Hub 环境真实业务规则（2026-08-25 已确认）

以下规则由负责人在与采购同事核对真实采购场景后确认。它们是后续采购执行设计的业务基线；当前测试版“认领后先保存分单、再进入采购执行”的流程仅是早期联调实现，不代表最终业务流程。

### 页面与人员边界

- “采购任务”是采购团队多用户共用的任务池，默认展示待认领采购单；认领解决任务归属问题，不负责提前确定实际下单批次。
- “采购执行”是当前采购员的个人工作台，展示本人已经认领并需要继续采购、付款、查单和跟单的采购单数据。
- 采购单被认领后应进入当前采购员的采购执行范围，但不能因为尚未提前分单而被排除在采购执行列表之外。
- 每张采购单必须保留明确的运营归属。运营归属随采购需求进入采购中心并贯穿认领、下单、付款和跟单流程；采购认领只新增或改变采购员归属，不得覆盖绑定运营。后续业绩统计需要同时支持按运营个人、采购员个人和团队口径汇总。

### 分单只能在真实下单与付款阶段确定

- 是否需要分单、每个采购批次包含哪些 SKU 和数量，通常必须等采购员进入真实下单、付款阶段后，结合买家号实际可用优惠券、店铺优惠门槛、商品组合、件数和实付情况才能确定。
- 因此，系统不能要求采购员在认领后、进入真实采购前一次性确定并保存最终分单方案；付款前的组合只能是可修改的下单尝试，实际下单/付款结果才形成正式采购批次。
- 一单一 SKU 一件：组合确定，可以走快捷下单/快捷生成单个采购批次并绑定资源。
- 一单一 SKU 多件：必须在下单付款时决定本批数量；可能按一件一批，也可能一批购买两件或更多，取决于当时优惠券规则。
- 一单多 SKU 多件：同样在下单付款时决定本批 SKU 组合和数量，不能在认领阶段固化分单结果。
- 后续实现必须持续记录每条采购需求的需求数量、已实际采购数量、当前尝试占用数量和剩余数量，避免重复采购或超买；具体状态机与锁定时点仍需在实现方案中确认。

### 买家号与 Hub 采购环境不是同一种资源

- 买家号是可继续使用的账号资产；Hub 采购环境是一次下单过程使用的浏览器环境，二者必须分别建模、分别管理生命周期。
- Hub 环境一旦登录过某个买家号，就不能解除后重新放回公共资源池，也不能再分配给其他买家号。
- 已登录环境发生下单失败或采购员主动放弃时：买家号解除本次占用，原则上可以继续使用；该 Hub 环境必须退出可用池并在 Hub 中直接删除。若失败原因涉及账号风控或账号异常，买家号应转人工检查，不能直接恢复可用。
- 付款成功时：Hub 环境不得删除，必须继续与实际采购订单/采购批次保持绑定，用于后续查单、跟单、物流信息补充和售后处理；该环境虽然保留，但仍不能回到公共资源池复用。
- 付款成功环境后续何时归档或清理、成功订单对应买家号何时可以再次参与其他采购，以及尚未登录买家号就取消的环境是否允许回池，当前均为待确认实现规则，不得自行假定。

### 对当前测试实现的影响

- 当前测试版 `claimed -> 保存采购分单 -> waiting_binding` 链路需要重新设计：认领成功后应直接进入个人采购执行；“未提前分单”不能成为不可执行状态。
- 前端“创建采购分单”不应作为认领后的必经步骤。后续更适合围绕“开始下单”“本次下单”“采购批次”和“继续采购”组织交互，但最终术语和操作步骤继续讨论后确定。
- 当前数据库中的采购分单表和测试数据可以作为早期验证结构保留参考，但不能直接视为最终领域模型；正式实现前必须重新确认下单尝试、正式采购批次、数量占用、付款结果、环境保留/删除和异常恢复之间的边界。

## 买家号与环境创建业务记忆

目标流程是“买家号先入库，再创建采购环境”：

1. 号商账号或未来自注册账号先进入买家号库。
2. 创建采购环境时只配置站点、环境数量、采购员分配等业务参数。
3. 后端从符合条件的可用买家号中分配并预占账号。
4. 本地执行器创建 HubStudio 环境、绑定账号/Cookie，并后台无头验证全部出口 IP。
5. 成功后写回绑定环境、采购员、状态和验证结果；失败时释放未使用预占，结果不确定时进入人工复核。

目前“买家号先入库”及现有环境创建已具备，但“按数量自动抽取、并发预占、超时释放”尚未实现，是资源中心后端的下一条核心业务链路。

## 不可破坏的安全约束

- 真实密码、Cookie、App Secret、访问令牌、代理链接和完整业务数据不得进入仓库、测试夹具、日志或截图。
- 所有真实平台写入必须保留明确确认；HubStudio 写入与飞书写入分别确认。
- 飞书写入必须先做字段/冲突预检，并在写后回读确认；不确定结果不能记为成功。
- API 错误和进度信息必须脱敏；公开配置接口不得回显 Secret、完整飞书链接、Base Token 或 Table ID。
- 后端权限必须作为最终裁决，隐藏前端菜单不能替代接口鉴权。
- 非超级管理员不得读取或修改飞书企业应用凭证和模块连接配置；权限接入后，前端隐藏“飞书连接”，后端配置接口同时返回 403。
- `admin` 不是云端配置主体。即使其余业务权限全部开放，`/api/lark/config`、目标解析、连接验证及后续 `system.integration.manage` 配置接口都必须在后端拒绝 `admin`。
- `resource.ip.credential.manage` 只允许超级管理员；代理账号/密码不得进入前端、缓存、检测历史、日志或导出，检测完成后必须清除任务内存引用。
- 任务下发必须有幂等键、租约/超时、重试边界和审计记录，避免重复创建环境或重复写账。

## 2026-08-26 采购任务飞书镜像不可破坏约束

- PostgreSQL 是采购任务事实源，飞书 Base 只是协同镜像；Base 中的人工修改不得反向改变认领或执行状态。
- 主表和明细必须分别用 `orderKey`、`lineKey` 查重，并保存远端 `record_id`；重复键、记录映射冲突或远端记录消失必须停在冲突状态，不能另建副本掩盖问题。
- Worker 在领取 Outbox 前必须完成 38/59 字段、字段类型、单选项和明细关联目标预检；写入必须写后回读。
- 飞书 Bitable v1 关联写值是记录 ID 字符串数组；回读可能是含 `record_ids` 的嵌套结构，两种形态都必须覆盖测试。
- 采购明细与正式采购批次是一对多关系。当前 Base 的实际付款/物流字段是单值字段，P0 不做有损覆盖，也不清空人工附件；聚合或拆表口径确认后再扩展。
- `0013_purchase_task_feishu_mirror` 与 Worker 已通过云端 70 项合成回归和临时 PostgreSQL 迁移往返，但尚未部署、尚未真实写采购 Base。功能默认关闭；首次 canary 必须另行授权并使用全新脱敏业务键。

## 2026-08-26 采购协作导入云端化决策

- “采购协作导入”属于云端可独立完成的文件解析与飞书外部服务集成，不依赖 HubStudio/CDP/SHEIN，因此迁入云端控制面；本地执行器继续保留兼容回退，但不再作为目标用户流程前置。
- 本地与云端必须共用同一解析、表头契约、稳定批次和幂等算法。云端构建前由同步脚本复制 canonical parser，并由测试阻止副本漂移；不得另写一套 XYP2 解析逻辑。
- 云端普通电子表格访问固定使用企业应用身份和文档应用授权，不为了本功能保存员工飞书 refresh token。飞书 OAuth 登录仍只识别 Xynigo 用户，两个鉴权域继续分离。
- 店小秘导出中包含完整收件信息和图片。云端只能将其保存为租户隔离、应用层认证加密、短时有效的计划；过期必须清空密文。任务表和日志只保存计数、状态和稳定错误码。
- 同一目标表/工作表/导入批次同时只能有一个非终态任务；数据库部分唯一索引是最终并发闸门。云端或 Worker 重启后必须基于现有导入批次、行签名与回读续作，不能按按钮调用次数重复追加。
- 官方 OpenAPI 无背景色读取能力时，安全优先于视觉补全：云端只给本次确认的新追加行设置分组底色，任何启动前已有行都视为可能存在采购员手工任务色并保留。表头批注不是 P0 云端成功判据。
- `0014_proc_import_cloud` 和云端 API/Worker 已部署到共享测试，功能开关已启用；部署只验证租户令牌、解析/导出与空任务表，没有写真实飞书。首次真实写入仍必须使用全新脱敏普通表格 canary，并明确指定目标表。

## 2026-08-26 桌面启动入口决策

- 普通用户双击默认启动器时，浏览器进入云端工作台；本地执行器进程仍启动，用于保留 HubStudio/CDP/SHEIN 等本机能力和后续设备通道。
- 旧本机 Web UI 不删除，统一通过 `--local-ui` 显式进入。双平台绿色包必须同时提供可见的“启动-本地执行器”入口，避免依赖用户手工拼接 localhost 地址。
- 云端部署不会改变已经安装的桌面二进制。该行为只有在新客户端版本通过绿色包或在线更新安装后才生效；不得用同一版本号发布不同内容的安装包。
- 2026-08-26 `v0.12.4` 已作为 Latest、非 prerelease 发布，公开提交为 `9fc1eae7f212e902f0759919e45e1fa3c825b18b`；云端页面、OpenAPI、更新清单和双平台执行器版本均已对齐。

## 2026-08-26 收工长期复盘

### 版本、发布与部署是三套独立事实

- 以后任何“当前版本”必须同时列出：内部源码 HEAD/`__version__`、共享云端页面与 OpenAPI、GitHub Latest/manifest。窄热修复可能只替换 parser 或 gateway，不能因为业务修复已上线就把云端称为完整新版本。
- 正式发布固定顺序：内部全量回归 → 公开净化 worktree 与安全审计 → 公开分支 CI 全绿 → 云端完整版本和健康验证 → 注释标签 → 标签 CI 全绿 → GitHub Latest → 旧版更新器真实发现。任一阶段失败都停在候选，不自动跨闸门。
- 同一版本号不得发布不同内容。云端部署也不会改变员工电脑上的旧二进制；执行器行为只能通过新绿色包和用户确认更新生效。
- `v0.12.5` 已于 2026-08-27 完成发布：内部 HEAD `bad70b0`，共享云端为 `0.12.5`，公开标签指向 `6ba9ade598c9cf118efc15ce8cf3a3cbe2b7d43e`。分支与标签两轮六任务 CI 均通过，Latest 和双平台更新清单已回读；这仍不是生产部署。

### 并行开发与部署必须先做差异盘点

- 多任务并行时，远端容器可能在当前会话之外刚被替换。部署前先看容器 `StartedAt`、镜像 ID、迁移和健康，再比较 `main.py / __init__.py / web/index.html / procurement_import_core.py / procurement_import_sheet.py / procurement_import_service.py / procurement_import_xlsx.py` 哈希。
- 如果远端已有较新的其他修复，不能用本地完整镜像盲目覆盖。可基于当前运行镜像构建窄热修复，但必须记录哪些文件已替换、哪些仍漂移，并保留旧镜像标签和应用快照。
- 用户或并行任务的 `docs/品牌VI资产/`、`outputs/`、业务 Excel/截图和独立部署 helper 都不应被顺手纳入当前提交。公开分支只从上一公开标签创建独立 worktree，并复制明确 allowlist。
- 执行 Git 操作前始终确认 `pwd` 与 `git status`。特别是 `git add -A`，只能在目标公开 worktree 使用；若在内部根目录误暂存且尚未提交，只恢复索引，不回退工作树。

### 采购协作导入的长期边界

- 普通 Sheet 导入是追加/防重工具，不是订单修订工具。历史订单完全一致时整单跳过，即使已有多个完整相同副本也不继续制造重复；历史业务明细不同必须在追加任何新行前阻断。
- PostgreSQL 采购任务的“认领前修订”是另一条链路，不能通过重新导入协作表绕过认领、分单或执行状态。
- 同一 XYP2 采购明细可能汇总店小秘多个销售产品行。必须聚合全部精确匹配来源行的数量、商品金额和可用图片，再与 XYP2 核对；不能只取一条代表行并把其余行误报为未匹配。
- 已存在历史行视为采购人工状态，不补写或覆盖其业务字段、链接、图片、行高和任务底色。OpenAPI 不能可靠读取历史背景色时，默认保留优先于视觉一致。
- 导入任务的 failed/completed/expired 记录是审计和复盘证据。过期计划清空密文，但任务状态、计数和稳定错误码保留；不得自动删除失败任务、伪改 completed 或无判断重跑。

### 云端安全与可恢复部署经验

- 店小秘文件含完整收件信息和图片，只能进入租户隔离、短时、AES-GCM 密文计划；日志、审计和持久化进度只存计数、状态、稳定错误码，不存订单号、地址、链接或图片。
- 部署前数据库 dump 必须生成 SHA-256 和 `pg_restore -l` 清单；涉及迁移时恢复到临时数据库验证。应用、`.env`、Nginx 和运行镜像分别留回滚点，数据库 downgrade 不是撤销飞书外部写入的手段。
- 服务器首次完整 Docker 构建可能因重复下载大依赖长时间阻塞。可以用已验证运行镜像作基线，再用锁文件校验并只安装新增依赖；这不是跳过依赖锁，也不能复用来源不明的镜像。
- SSH heredoc 中的 `docker compose exec -T` 会读取脚本 stdin。非交互 compose exec/run 必须显式 `</dev/null`，dump/restore 单独重定向；否则脚本可能在第一条 exec 后悄然结束，只留下半套备份。
- 远端 SQL、正则、`$()` 和管道容易被本地 shell 提前展开。复杂脚本优先使用单引号 heredoc，输出只留版本、状态、计数和哈希，不打印 `.env` 值、token、订单或收件信息。

### 客户端入口的真实能力边界

- `v0.12.4` 默认启动器打开云端，但本地执行器仍是独立进程；云端页面目前没有通用设备配对/心跳/租约通道，不能直接调用本机 HubStudio/CDP/SHEIN。
- 双平台包必须长期保留可见的“启动-本地执行器”入口和 `--local-ui`，直到设备通道完成并通过断网、超时、重复领取、撤销和审计验收。
- GitHub manifest 被下载或安装包出现下载计数，不等于同事完成更新。真实验收至少需要 Windows/macOS 各一台，核对版本、默认云端、本机兼容入口、配置/日志/运行数据保留和失败回滚。
