## 2. 已确认的字段口径

| 字段 | 口径 |
|---|---|
| 订单商品总件数 | 按整单商品实际数量合计，不按图片数、商品种类数或包裹数推断 |
| 单件订单 | 商品总件数 = 1 |
| 多件订单 | 商品总件数 ≥ 2；同款购买 2 件也属于多件 |
| 件数待核对 | 未采集到数量或数据不完整，不能默认算单件或将未知值按 0 处理 |
| 商品明细 | 展示商品图、商品标识/名称、规格及每项数量；商品数量与可退包裹数分开 |
| 送达日期 | 以平台展示的送达日期筛选，含起止日，不擅自转换时区 |
| 送达时间缺失 | 明确标识，不用下单时间、预计送达时间或退货截止时间替代 |
| 订单金额合计 | 仅用于选单核对，不表述为预计或最终退款金额 |

“整单商品数量”与“当前可退包裹内商品数量”不可混用。若现有接口只能返回可退包裹商品，必须补齐整单来源或标记未知，不能据此认定整单单件/多件。跨包裹重复商品须按稳定商品行标识及实际数量处理，不能简单按图片 URL 去重。

## 3. 筛选、勾选与提交

1. 日期：支持起始日、截止日、仅填一端；起止日均包含。起始日晚于截止日时提示无效范围并阻止该范围选单。
2. 件数：全部、单件订单、多件订单、待核对；与日期、申请状态筛选取交集。
3. 日期缺失：有日期范围时不纳入；提供“仅看送达时间缺失”。件数未知不进入单件或多件筛选结果。
4. 申请状态：全部状态、仅可申请、暂不可申请；非可申请订单不能勾选。
5. 展示“扫描总数 / 当前显示数 / 当前可申请数”，区分全部扫描结果与筛选子集。
6. 批量勾选仅作用于当前筛选结果中的可申请订单；表头复选框支持全选及部分选中状态。
7. 修改任何筛选条件时清空勾选，并在有原选择时提示清空数量，避免提交被隐藏的订单；重置筛选恢复全部结果。
8. 底部展示已选订单数及订单金额合计；未选择时禁用提交。
9. “核对并提交售后”打开确认弹层，列出订单、环境、日期、件数，并汇总单件/多件/待核对订单数；支持返回修改。
10. 正式提交前仍使用平台实时资格核验，退款原路退回；日期与件数筛选不能代替资格校验，也不改变现有防重复提交与可靠回传机制。

## 4. 商品图与采集链路

现状已通过源码确认：

- `src/purchase_tool/after_sale_claim.py` 的订单卡片采集使用首个商品图片元素。
- 同文件售后预查询将包裹 `item_list` 投影为首个商品的 `goods_img`，丢弃其余商品及数量。
- `src/purchase_tool/operation_executor.py` 的扫描行投影优先使用首个可退包裹的 `goodsImg`。
- Web 当前每单仅接收一个 `goodsImg`，不能表示多商品订单。

这能解释多商品订单只显示一张图，但不能直接证明跨订单图片重复的原因；相同首商品或图片取错仍需真实样本核对，不能猜测。

目标设计：一行一单，展示多商品缩略图；点击打开明细，明确款数与件数。同款多件不必重复画相同缩略图，但必须展示数量。缩略图数量有限时须标识还有更多商品，完整明细不能丢失。示意原型展示前三款；正式实现需覆盖超过三款的情况。

开发影响面：执行器商品明细采集 → 扫描结果投影 → 云端闭集契约与快照 → Web 筛选/展示。不能只改页面或把可退包裹数当作商品件数。新字段需兼容历史记录和旧执行器，缺失按“待核对”显示；具体字段名、数量来源与能力门槛在开发前核验。

## 9. 测试补充：不可申请原因具体化

用户反馈：扫描清单将多条订单标为“暂不可申请”，说明统一为“平台显示退款处理中或审核中；当前没有丢件退款申请入口”。该文案不能区分当前真实退款阶段，也不能解释缺少入口的具体业务原因。

确认需求：

- 分开显示“申请资格”和“具体原因/平台状态”。例如，证据明确时分别展示“已有退款申请 · 审核中”“已有退款申请 · 退款处理中”“已退款”，不将不同阶段合并为“处理中或审核中”。这些是展示示例，不代表截图中订单的真实阶段已经核实。
- 对其他不可申请情形，同样按证据区分运输中/未送达、申请期限已过、订单已取消、平台明确限制等；没有明确证据时不可自行归因。
- “没有申请入口”仅表示观察结果，不等同于“已退款”“已提交过”或“已过期”。若只确认入口缺失，应展示“未发现丢件退款入口 · 具体原因待核对”；若平台只提供笼统状态，则展示该状态并注明详细阶段未确认。
- 支持查看平台原文和最近读取时间，以便人工核对；有明确关联退款单时可展示退款单号，并引导至退款跟踪读取具体阶段，不能凭订单状态猜测退款进度。
- 清单与 Excel 导出的原因应一致，长原因可展开完整查看，不只保留截断后的文本。
- 原因判定与最终可申请性分离；能否提交仍以平台实时资格核验为准，不因优化文案放宽提交限制。

验收覆盖：审核中、处理中、已退款、运输中、明确过期、入口缺失但原因未知，以及读取失败/无法识别。未知或失败不得伪装成确定的业务状态。当前仅记录需求，未核实截图每单的实际退款阶段，未修改代码、原型或线上服务。

## 10. 提交阶段核验与回执异常（后续测试，优先处理）

现象：扫描标记可申请的订单，进入提交批次后部分返回“不可申请 · 已提交过”，备注却是“该订单已无可申请售后的包裹（可能已提交过）”。另有订单出现平台成功发送退款提示，但被脚本记为“提交后未跳转成功页”的失败。

只读检查结论：

- 当前代码将提交前 `eligible` 为空映射为 `blocked`，前端和 Excel 再将所有 blocked 固定描述为“已提交过”。空列表只能证明本次核验没有可申请包裹，不能独立证明提交历史。
- `_submit_package` 以跳转成功页及取得退款号判断成功；即便出现 `Reembolso enviado correctamente.`，未检测到跳转时仍返回普通失败。平台受理与本地回执不一致，不能将此类行直接作为安全可重试失败。
- 真机抽查两条 blocked 行及一条带成功提示的 fail 行，平台均显示卖家/SHEIN审核中、无新的申请入口。真实订单映射保留私有核对记录；不能据此推断本批全部行都相同，或确定全部申请发生于本次执行。
- 核对结束时该批次已停止：9 条 blocked、6 条 fail、20 条 stopped。这是执行器分类，不能解释为“6 次退款申请一定未成功”。未触发补提、重新提交或平台状态修改。

待修要求：

1. 提交结果不能把所有 blocked 都标为“已提交过”；根据平台明确证据给原因，证据缺失时显示“当前无可申请包裹 · 具体原因待核对”。同步修正当前结果、历史及 Excel。
2. 将“写操作已触发、受理回执不完整”与“提交前失败”分开。成功提示但缺退款号、提交后超时等应进入待核对，禁止直接进入批量补提。
3. 只读核对平台退款记录并补取退款号、申请时间及当前阶段；回执恢复不能再次调用创建退款接口。需验证写入是否成功时保留不确定状态，不能由页面跳转失败推断退款未提交。
4. 对比扫描时间、提交前核验时间、平台申请时间及批次历史，定位扫描到提交之间的状态差异；目前具体变化时点未核实，不猜测为用户重复操作、其他人操作或平台过期。

本节为新增问题记录及诊断结论；尚未实现提交回执恢复和待核对补提隔离。此前扫描原因修复不能被当作此问题已经解决。

## 12. 提交结果：状态与备注必须精准一致

用户再次明确：提交结果若确定是“不可申请 · 已提交过”，备注必须反馈已核实的准确原因，不能仍写“该订单已无可申请售后的包裹（可能已提交过）”。

当前矛盾来源：执行器根据可申请包裹列表为空返回 `blocked` 和推测性备注，前端却将 `blocked` 固定映射成确定的“已提交过”。二者都缺少足以证明具体原因的关联退款记录，不能只删掉“可能”来修复。

验收规则：

- 状态与备注共用同一份核实结果。只有明确关联到该订单/包裹的已存在退款申请，才显示“不可申请 · 已提交过”。
- 确认已有申请时，备注示例：“该订单已有售后申请，当前为卖家/SHEIN审核中；退款单号：…；平台申请时间：…”。处理阶段不同应展示真实阶段。单号和时间只展示实际取得的数据，时间保留可核实的时区；缺字段明确说明未取得，不能补造。
- 确认其他原因时，状态及备注分别准确表达运输中、明确超过申请期限、订单取消、退款已处理等实际证据；不将这些原因统一写为“已提交过”。
- 若只知道可申请包裹为空，显示“当前不可申请 · 原因待核对”，备注说明“平台资格核验未返回可申请包裹，尚未确认具体限制原因”，不能确定归因为已有申请。
- 当前结果、历史详情、Excel 使用同一原因口径，并区分本次核验与历史记录；旧备注不能未经重新核对就改写成确定原因。
