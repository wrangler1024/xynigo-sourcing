# 阶段 2 云端运行链路交付说明

## 目标

把“页面等待本机 RPC 返回”的临时链路改为“云端 Run 是任务事实源、本地执行器只负责执行”的正式链路。页面刷新、重新登录或短时网络中断后，进度从 PostgreSQL 恢复，不重新向执行器读取整批历史结果。

## 已实现

- 新增环境创建、物流查询两类持久化 Run，支持幂等提交、执行器绑定、阶段、尝试次数、逐行进度、出口 IP 状态、安全停止和终态查询。
- 新增正式执行器任务：`environment.create-bound.v1`、`environment.create-backup.v1`、`logistics.query.v1`。
- 新增专用加密解析任务 `environment.parse.v1`。买家号 xlsx 在云端任务表中只保存加密信封，解析仍在指定本机执行器完成；云端只接收经过严格字段校验的脱敏预览和本地计划引用。
- 环境创建的站点、采购分组和采购员分配改为任务参数，不再依赖某台电脑保存的历史业务偏好。
- 执行器每次状态变化上传脱敏行快照；租约续期同时刷新 Run 心跳。云端拒绝未脱敏邮箱、额外凭证字段和不合法终态摘要。
- 云端 Web 的正式建环境、备用/测试环境、首次物流查询、单行重查和异常批量重查均提交 Run；页面轮询 Run API，并在刷新后读取当前用户最近一次 Run。
- 页面安全停止改为取消云端 Run 对应任务。执行器在续租响应中发现取消请求后，调用本机协作式停止，不强切正在写入的一整行。
- 本机任务完成后仍通过结果接口补齐完整业务结果和 Feishu outbox；Run 进度与最终结果使用同一 `runKey`，不会生成两份批次。

## 主要接口

- `POST /v1/environment-plans/parse`
- `POST /v1/operation-runs/environment-creation`
- `GET /v1/operation-runs/environment-creation/latest`
- `GET /v1/operation-runs/environment-creation/{run_id}`
- `POST /v1/operation-runs/environment-creation/{run_id}/cancel`
- `POST /v1/operation-runs/logistics-query`
- `GET /v1/operation-runs/logistics-query/latest`
- `GET /v1/operation-runs/logistics-query/{run_id}`
- `POST /v1/operation-runs/logistics-query/{run_id}/cancel`

## 现场问题覆盖

- 页面切回、刷新或重新登录后批量进度重新获取且卡顿：改为直接读云端 Run 和逐行结果。
- “正在提交”持续很久、执行器响应中断后不确定是否受理：创建 Run 后立即返回 `202` 和稳定任务编号，重复提交由幂等键去重。
- 任务状态反复跳动、执行完成后按钮仍长时间停留在执行中：统一使用 Run 状态和终态，不再拼接多条本机 RPC 状态。
- 查询物流开始按钮要点多次、重新查询无反应：首次查询和两类重查均成为正式任务，可查询、可取消、可恢复。
- 环境创建并发、出口 IP 检测和逐步状态不可见：云端持久化实际逐行步骤、成功/失败/停止计数和 IP 检测进度。
- 错误站点或采购分组导致解析/执行失败：正式任务显式携带并校验站点和采购分组；页面流程保持先选择站点/分组，再上传解析。

## 通道边界

当前仍使用出站 HTTPS 长轮询领取命令和续租。长轮询只承担命令通知与租约，不再承担页面批量进度查询；PostgreSQL Run 是任务事实源。后续如改 WSS，只替换通知层，Run、幂等、租约、停止和结果模型无需重做。
