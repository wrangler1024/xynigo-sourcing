## 已实现能力

### 云端 API

- `POST /v1/admin/members/invitations/resolve`：使用管理员输入的飞书绑定手机号，实时解析当前应用可见的企业成员，只返回候选人的脱敏展示信息和现有 Xynigo 成员摘要。
- `POST /v1/admin/members/invitations`：确认新增时由后端重新解析手机号，不信任浏览器保存的候选身份；创建后的成员状态固定为 `pending`。
- 未预分配角色时只要求 `system.member.manage`；预分配角色时额外要求 `system.role.manage`。
- 角色必须属于当前租户；非超级管理员不能分配超级管理员角色，也不能授予自身不具备的权限。
- 已存在成员、找不到成员、成员冻结/离职、飞书权限不足和飞书不可用均使用稳定错误码返回，并记录脱敏审计。

### 飞书通讯录调用

- 使用“小犀代采”应用的 `tenant_access_token` 调用通讯录，不持久化飞书访问令牌。
- 先调用 `POST /open-apis/contact/v3/users/batch_get_id?user_id_type=open_id` 将手机号精确解析为应用内 Open ID，再调用 `GET /open-apis/contact/v3/users/:open_id` 获取姓名、头像与账号状态。
- Xynigo 用户身份仍以 `tenant_key + open_id` 为主键；手机号只是查找输入，不是登录主键。
- 手机号不写入 Xynigo 数据库、API 响应或审计；浏览器不会获得飞书 Open ID。

### 系统管理前端

- “系统管理 → 组织与权限 → 成员管理”增加“新增成员”。
- 采用“输入手机号 → 查找飞书成员 → 展示候选人 → 可选预分配角色 → 单独确认新增”的两段式交互。
- 页面明确提示新增后仍为 `pending`，角色预分配不会自动批准成员。
- 修改手机号会清除候选状态；取消会清空输入、候选人和角色选择。

## 飞书后台配置基线

按最小权限原则，当前流程需要以下应用身份权限：

- `contact:user.id:readonly`：通过手机号或邮箱获取用户 ID。
- `contact:contact.base:readonly`：调用单个用户信息接口。
- `contact:user.base:readonly`：返回姓名、头像等用户基本信息。
- `contact:user.employee:readonly`：返回激活、冻结、离职等成员状态。

无需开通 `contact:user.phone:readonly`；Xynigo 不读取或保存成员手机号字段。

通讯录数据权限范围必须覆盖待查找成员，应用可用范围必须覆盖需要完成飞书 OAuth 登录的成员。两者可以设置为“与应用的可用范围一致”或按部门配置，不要求逐人维护。飞书范围与暂不开发的 Xynigo 业务“数据范围”不是同一功能。

权限和范围发布审核生效后不需要重启 Xynigo：每次查找都会重新获取应用身份令牌并访问飞书。
