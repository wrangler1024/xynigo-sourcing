# 20260916 需求 · 解除售后页面前置锁：支持直接提交指定单

状态：**需求记录，尚未实现**（Jeff 20260916 提出，记为待排期）
基线：`origin/main` `b7799e1`（文中行号均按此版本）
关联：`docs/20260915_采购售后模块交接.md`（模块总交接）、采购中心 › 采购售后 › 丢件退款

## 1. 背景

当前 ③ 提交结果 的「提交售后」按钮，置灰条件是「② 可申请清单 里勾了单」，而 ② 的行只可能来自扫描。于是即使采购已经确定要售后哪些订单（例如按物流台账点名单），也必须先把环境扫一遍才能提交。

## 2. 核查结论（为什么说这是界面锁，不是安全前提）

三层都核过，**执行器与云端都不要求先扫描**：

| 层 | 依据 | 结论 |
|---|---|---|
| 云端 | `cloud/auth-service/src/xynigo_auth/main.py:5416` → `operation_service.py:414` | 建 Run 只校验请求体里的 items，不检查是否扫描过 |
| 执行器 | `operation_executor.py:785` → `Main.after_sale_claim:811`（`_claim_one`） | 拿到 `环境序号 + 订单号` 直接跳申请页；提交前现场调 `pre_info`（`after_sale_claim.py:827`）判可退性 |
| Web | `index.html`：`asSelectedItems()`（5337）、`asSyncSelection()`、`asSubmit()` | 唯一加锁处：items 取自 ② 的勾选行 |

也就是说：扫描的作用是「把可提交的单挑进 ② 让你勾选」，安全闸门在提交侧的二次体检（不能退的判 `blocked` 写入备注，算「已跳过」不算失败）。

## 3. 需求

1. **解除前置锁**：③ 允许在没有 ② 勾选行的情况下提交（扫描不再是必经步骤）。
2. **新增「直接提交指定单」入口**：粘贴 `环境序号 订单号`（多组用分号或换行分隔）→ 点击后直接建 Run 提交。形态对齐 ④ 已有的「回访指定单」。
3. **保留扫描为默认推荐路径**：扫描能预先看到金额/包裹数、避免白跑，界面上仍作为首选，手工入口作为补充。

## 4. 验收标准

- 未扫描时也能提交：粘贴 2 组 → 建成 Run → 执行器逐单串行提交；能退的 `ok`，不能退的 `blocked` 且备注写明原因。
- 幂等：重复提交同一单，平台把已提交包裹划入不可退 → `blocked`，不产生重复退款。
- 解析容错：多余空格、中文/英文逗号、分号、换行都能正确分组；**字段不足的组要给出明确提示，不静默丢弃**。
- 与 ④ 的关系不变：手工提交的退款单号照常回传，④ 可直接回访。

## 5. 同源缺陷（建议同批修）

它们与本次需求出自同一处「字段/界面没跟上」，建议一起做：

1. **商品图、送达时间在 ③ 里为空**——链路上被丢了两处：
   - Web `asSelectedItems()`（`index.html:5337`）只带了环境序号/订单号/店铺/包裹号；
   - 执行器桥接层 `_execute_after_sale_claim` 的 clean 列表（`operation_executor.py:800`）同样只保留四个字段。
   - 云端契约（`AfterSaleClaimItem`）、云端落库（`executor_service.py:2612`）、执行器本地投影（`after_sale_claim.py:863`）三处**都已就绪**。真机 4589/4598 两单在库里这两列就是 `null`，即此处。
2. **③ 列序**：`环境序号` 移到最前（表头与行模板、以及钉列序的测试同步改）。

注意：从手工入口进来的单本来就没有这两列内容（它们是扫描阶段带下来的），属预期，不算缺陷。
