## 1. 背景

③ 提交结果只活在当前页面会话里：刷新后靠 `GET /v1/operation-runs/after-sale-claim/latest` 恢复**最近一批**，往期批次看不到；要跟进退款，得在 ④ 手工把 `环境序号 订单号 退款单号` 一行行粘进去。也就是「提交过什么、结果如何」和「这批现在退到哪了」两件事之间没有连接。

Jeff 要求：③ 支持提交历史（仿照物流查询、创建环境的操作历史），并且**退款跟踪可以直接从提交历史发起查询跟进**。

## 3. 需求

1. **③ 增加「提交历史」入口**（按钮 + 弹层）。列表每行＝一个提交批次：时间、操作人、执行器、环境数与单数、成功／已跳过／失败计数、状态；支持按状态筛选、按操作人筛选（管理员）、cursor 分页。
2. **批次详情**：该批次的逐单结果，列与 ③ 一致（环境序号／订单号／商品图／售后类型／送达时间／退款单号／退款路径／退款信用卡／状态／操作时间／备注），失败行能看到失败原因。
3. **从历史直接跟进退款**：详情里加「回访本批退款单」——把该批次中**有退款单号的行走**灌进 ④ 发起回访（等价于 ④「回访指定单」的批量版）。④ 的链路不改，只是多一个入口。
4. **再次提交失败单**：批次详情里对失败行发起重提（Jeff 20260916 拍板要，不再是可选项）。重提走同一套建 Run + 执行器提交链，形成**新批次**。

> 见 `docs/20260916_售后需求排期与暂缓.md`。本需求里的批次详情重提入口**复用同一个动作**，不重写。

## 4. 验收标准

- 列表 cursor 分页正确，翻页不重不漏；**普通用户只看到自己的批次，管理员能看全租户**（两条各有一个测试兜住）。
- 批次详情的行数与成功／跳过／失败计数，与该批次当时在 ③ 的显示一致（同源快照）。
- 从历史发起回访：④ 拿到的退款单号集合＝该批次有退款单号的行；回访任务与手工粘贴走的是**同一套建任务口径**（不新增第二条回访路径）。
- 历史查询本身只读，不得触发写操作；「再次提交失败单」是唯一从历史发起的写动作，必须二次确认。
- 「再次提交失败单」只针对**可恢复的失败**：`fail` / `login` / `inuse` / `stopped`。
  **不含 `blocked`**——blocked 是平台判定「已无可退包裹」，重提只会再 blocked 一遍（写操作白跑），
  界面上这类行的重提入口不出现。
- 重提产生新批次，新批次在列表里能看出「重提自哪一批」。实现倾向：用审计的 `change_summary`
  记录来源批次 id，**不加数据库列、不加迁移**；若实现时发现审计里读不到，再考虑加列。
- 从历史发起的回访，与 ④ 手工粘贴走同一套建任务口径（不新增第二条回访路径）。
- 批次详情导出 Excel：列与 ③ 一致；空值留空单元格（不写「—」占位符），商品图列写 CDN 链接不内嵌图片
  ——与已实现的 ④ 退款跟踪导出口径保持一致。
