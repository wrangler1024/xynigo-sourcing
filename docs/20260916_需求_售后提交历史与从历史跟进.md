# 20260916 需求 · 售后提交历史 + 从提交历史直接跟进退款

## 1. 背景

③ 提交结果只活在当前页面会话里：刷新后靠 `GET /v1/operation-runs/after-sale-claim/latest` 恢复**最近一批**，往期批次看不到；要跟进退款，得在 ④ 手工把 `环境序号 订单号 退款单号` 一行行粘进去。也就是「提交过什么、结果如何」和「这批现在退到哪了」两件事之间没有连接。

Jeff 要求：③ 支持提交历史（仿照物流查询、创建环境的操作历史），并且**退款跟踪可以直接从提交历史发起查询跟进**。

## 2. 现有可照抄的形态（已核）

| 环节 | 物流查询 | 创建环境 |
|---|---|---|
| 列表 | `GET /v1/operation-runs/logistics-query/history`（`main.py:4659`） | `GET /v1/operation-runs/environment-creation/history`（`main.py:4038`） |
| 详情 | `.../history/{root_run_id}`（`main.py:4722`） | `main.py:4095` |
| 参数 | `limit`(1~100) / `cursor` / `status` / `site` / `userId`（仅管理员可查他人） | 同左 |
| 可见范围 | 普通用户只看自己的，管理员看全租户（`history_admin`） | 同左 |
| Web 形态 | `btnQueryHistory` 弹层（`query-history-*`） | `btnEnvironmentHistory` 弹层（`environmentHistory*`），含分页/详情/返回 |

关键先例：**建环境的历史详情里已经有「从历史发起动作」**——`loadInterruptedEnvironment(...)`（`index.html:10391`，用于中断任务续跑）。「从提交历史发起回访」就是同一形态，不需要新造交互。

售后侧已有的相邻端点：`GET /v1/operation-runs/after-sale-claim/latest`（`main.py:5502` 附近，权限 `assistant.access`）——新的列表/详情沿用同一套权限与可见范围口径。

## 3. 需求

1. **③ 增加「提交历史」入口**（按钮 + 弹层）。列表每行＝一个提交批次：时间、操作人、执行器、环境数与单数、成功／已跳过／失败计数、状态；支持按状态筛选、按操作人筛选（管理员）、cursor 分页。
2. **批次详情**：该批次的逐单结果，列与 ③ 一致（环境序号／订单号／商品图／售后类型／送达时间／退款单号／退款路径／退款信用卡／状态／操作时间／备注），失败行能看到失败原因。
3. **从历史直接跟进退款**：详情里加「回访本批退款单」——把该批次中**有退款单号的行走**灌进 ④ 发起回访（等价于 ④「回访指定单」的批量版）。④ 的链路不改，只是多一个入口。
4. （可选，待定）从历史批次「再次提交失败单」——与「直接提交指定单」需求天然重合，建议合并考虑。

## 4. 验收标准

- 列表 cursor 分页正确，翻页不重不漏；**普通用户只看到自己的批次，管理员能看全租户**（两条各有一个测试兜住）。
- 批次详情的行数与成功／跳过／失败计数，与该批次当时在 ③ 的显示一致（同源快照）。
- 从历史发起回访：④ 拿到的退款单号集合＝该批次有退款单号的行；回访任务与手工粘贴走的是**同一套建任务口径**（不新增第二条回访路径）。
- 历史是只读的：查询历史不得触发任何写操作；若做「再次提交」，必须显式二次确认。

## 5. 改动面（预估）

- **云端**：新增两个端点（列表 / 详情）+ 服务层快照函数；详情复用既有 `after_sale_claim_snapshot`，**不新增表**；审计动作按既有命名（`assistant.after_sale.claim.history.list|read`）。
- **Web（权威源）**：③ 加历史按钮与弹层（照 `environmentHistory*` 那套结构）；详情加「回访本批退款单」接 ④。改完必跑 `sync_web_workspace.py`。
- **执行器**：无需改动。
- **测试**：云端历史列表/详情/可见范围；Web 接线与契约对齐。
