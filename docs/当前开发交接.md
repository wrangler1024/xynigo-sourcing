## 成员准入规则

“能在飞书看到授权页”和“能进入 Xynigo”是两个阶段：

1. 成员必须位于“小犀代采”应用的飞书可用范围内，才能正常发起授权。
2. OAuth 返回的 `tenant_key` 必须在 Xynigo 云端租户白名单中。
3. 未知成员首次授权只创建 `users.status=pending`，不会签发系统会话。
4. 只有 `active` 成员才能登录；`disabled` 成员必须被拒绝。
5. 新成员自动激活默认关闭；只有环境变量中明确指定的超级管理员可在首次登录时激活并初始化超级管理员权限。
6. 成员激活后仍必须分配角色和权限，模块显示与业务 API 均按权限裁决。

当前没有成员审批、角色分配和会话管理页面，也没有对应的完整管理员 API。因此除已配置超级管理员外，其他企业成员即使完成飞书授权也会停留在待审批状态。

## 当前卡点

- 成员审批、角色授权和会话撤销只有数据模型/权限码，缺少管理员 API 和系统管理页面。
- “小犀代采”应用的最终成员可用范围尚未在项目文档中形成验收记录；普通成员真实联调还未完成。
- 飞书令牌端对当前应用的 PKCE challenge 返回 `20049`。测试实例暂时将 `XYNIGO_AUTH_FEISHU_PKCE_METHOD` 设为 `disabled`；随机 state、五分钟有效期、摘要存储和单次消费仍启用。飞书侧兼容后优先恢复 S256。
- 云端仍是单机测试实例：备份只有同机副本，缺少异机备份、保留周期、失败告警和高可用。
- 正式绿色包、Windows Keychain/DPAPI 实机联调和现有采购员灰度尚未完成，不能把当前测试登录直接视为正式上线。
- 交接时观察到一个长期未退出的远程 `docker compose up -d --build` SSH 终端会话，但云端健康和就绪检查正常。新会话先只读确认终端/进程状态，不要根据这一条记录直接终止它。

## 已知踩坑与处理经验

- 飞书回调 URL 必须逐字符一致；未登记精确地址会出现 `20029`。
- 当前应用的 S256 和 plain PKCE 令牌交换均出现 `20049`；兼容开关只作为受控临时措施，代码默认值仍保持 S256。
- 飞书登录必须使用“小犀代采”应用，不能误切回仅个人使用的 `samforo-cli`。
- 飞书 OAuth 用户身份与多维表格 OpenAPI 企业凭证不能混用；前者识别用户，后者代表服务访问业务表。
- 本地登录不能把云端会话交给网页保存；必须由本地服务通过一次性轮询桥换取并写入系统安全存储。
- 只隐藏前端菜单不构成权限控制；本地业务接口、云端管理员接口和飞书配置接口都必须各自校验权限。
- `python -m purchase_tool --help` 不会显示帮助，而会按普通入口启动一个新服务；当前入口只识别 `--no-browser`。检查端口前不要运行 `--help`。
- 本地端口被占用时会从 `config.json` 的 `serverPort` 起自动尝试后续 9 个端口。页面和测试必须使用启动窗口实际打印的 URL，不能硬编码认为一定是 8767。
- 多开本地服务时，停止前先用 `lsof -nP -iTCP:<port> -sTCP:LISTEN` 精确确认 PID；不要批量结束所有 Python 进程。
- 直接展示云端 OAuth 回调页面曾受应用内浏览器客户端策略影响；应以本地一次性登录桥、云端审计/会话记录和本地页面状态共同验收。
- 服务器从 PyPI 首次构建镜像较慢；依赖没有变化时优先复用镜像缓存，不要因等待时间长重复执行多个构建。
