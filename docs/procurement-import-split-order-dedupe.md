# 采购手动拆单后的导入去重

采购将一单多明细中的销售订单号改成 `SYNTH-ORDER-1`、`SYNTH-ORDER-2` 后，重新导入原始 `SYNTH-ORDER` 应识别已有母单并跳过。导入不会覆盖采购子单号、采购员、执行状态、采购订单号、采购链接、图片或任务底色。

## 订单身份与字段约定

- **系统订单键**：导入时生成并保留，表示原始“店铺＋销售订单号＋包裹号”。采购拆单时不得修改或删除其单元格内容。
- **销售订单号**：兼容现有操作，允许采购在原号后追加 `-1`、`-2` 等数字子单后缀。去重时在内存中核实原始订单号，不回写或清除子单号。
- 原始订单身份与采购子单展示号分开参与处理，继续使用现有协作表字段，不需要迁移表头或历史业务数据。

系统先验证完整订单号与保留键是否一致；不一致时才检查数字后缀之前的候选母单，并要求母单的店铺、包裹号和原始订单号共同生成的键与保留键相同。原始订单号本身含数字后缀时，不会仅凭后缀被合并。旧版 `店铺|订单号|包裹号` 键仅在内存转换，继续兼容。

## 重复导入与异常处理

| 情况 | 结果 |
|---|---|
| 已拆单，系统订单键保留且明细一致 | 同批次重试、新批次重导均跳过已存在明细 |
| 同批次只有部分明细改了子单号 | 按母单核对完整明细，整单保留采购维护内容 |
| 已有拆单订单与新订单混合导入 | 跳过已有订单，仅追加新订单 |
| 数量、规格、指导价、采购备注或数据版本冲突 | 整批停止追加，不覆盖已有记录 |
| 已人工拆单，但目标表缺失或多出部分明细 | 停止追加，不按上传中断自动补行 |
| 未人工拆单的同批次上传中断 | 保留原有缺行续传机制 |
| 系统订单键无效，或不能对应当前店铺、包裹和订单号 | 停止导入，提示目标表行号和系统订单键问题 |
| 疑似本次母单的子单缺失系统订单键 | 停止导入，提示行号，不能猜测母子单关系 |
| 旧记录没有系统订单键，订单号和明细保持原样 | 仍按完整店铺、订单号、包裹号核对去重 |

本次兼容的是“不同明细加子单后缀”。把同一明细的数量再拆成多行、替换规格或修改采购需求，仍属于明细变化，需要独立修订流程。既有完整重复订单不会被自动删除；系统键缺失且来源无法确认的历史数据，需要核实后修复，不能通过去掉后缀直接合并。

## 验证

- `tests/test_procurement_import_dedupe.py`：合成订单覆盖同批次/跨批次、旧键、缺失或损坏键、原生数字后缀、重复明细、部分拆单以及混合新订单的追加与阻断。
- `cloud/auth-service/tests/test_procurement_import_cloud.py`：通过解析、校验、导入及状态接口，验证导入后人工加后缀，再次导入新增 0 行、已有 2 行，采购数据保持原样。
- 通过 `cloud/auth-service/deploy/sync_procurement_import_core.py` 同步本机与云端逻辑；回归使用合成数据和内存协作表，不写真实业务表。
