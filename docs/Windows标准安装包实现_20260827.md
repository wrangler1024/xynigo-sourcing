# Windows 标准安装包实现

日期：2026-08-27
状态：品牌安装向导、状态中心与托盘纵切面已完成；绿色版已升级为可直接运行的 `Xynigo.exe` 兜底包；签名、Windows 真机验收、发布和部署待完成

## 结论

Windows 标准安装包采用 NSIS 3.12，生成 Unicode `.exe`。安装范围固定为当前 Windows 用户，不请求管理员权限，不注册开机启动，不安装系统服务，也不引入 Electron/Tauri 桌面壳。安装器使用 Xynigo 品牌欢迎图、页眉图、定制文案和图形化旧绿色包迁移页；安装后由原生 Windows GUI 状态中心托管隐藏的 Python 执行器，并驻留系统托盘，不再要求普通用户保持黑色命令窗口。

标准安装包和绿色版不是互相替代的两个代码分支：两者复用同一份原生状态中心与 Python 执行器。标准包负责安装目录、协议注册和卸载；绿色版负责在标准包不可用、签名链未准备完成或安装权限受限时提供明确的人工解压兜底。

## 安装结果

- 开始菜单：`Xynigo Sourcing`、`本地执行器状态中心`、`卸载 Xynigo Sourcing`。
- 桌面快捷方式：安装时可选，默认不强制。
- 原生状态中心：显示云端通道、HubStudio、本机任务、版本、设备配对和最近心跳。
- 系统托盘菜单：状态中心、云端工作台、重启执行器、设备配对、日志目录、关于和安全退出。
- 后台执行器：状态中心使用 `pythonw.exe --no-browser` 启动；输出只进入本机日志。
- 自定义协议：当前用户注册 `xynigo://`。
- 添加/删除程序：写入当前用户的卸载信息。
- 自启动：不注册 `CurrentVersion\Run`，不创建计划任务或服务。
- UAC：`RequestExecutionLevel user`，正常安装不弹管理员授权。

## 版本与数据布局

```text
Xynigo Sourcing/
├── Xynigo.exe             # 品牌状态中心与托盘主程序
├── Xynigo.cmd             # 兼容/故障排查启动器
├── xynigo-logo.png
├── xynigo-x.ico
├── 配对本地执行器.cmd
├── current-version.txt
├── versions/
│   ├── 0.12.5/          # 示例；每个发布版本不可变
│   └── 下一版本/
├── config.json          # 用户数据，不在版本目录
├── 查询日志/            # 用户数据
└── 运行数据/            # 用户数据
```

新版本先安装到独立版本目录，再更新 `current-version.txt`。正在运行的旧版本不会被覆盖，下一次启动才切换到新版本。相同版本号的目录使用不可变策略，不允许借重新打包偷换内容；正式发布前必须提升版本号。

标准启动器固定以下环境：

- `XYNIGO_DATA_DIR`：安装根目录，确保 `config.json`、日志和运行数据跨版本共用。
- `XYNIGO_INSTALL_DIR`：安装根目录。
- `XYNIGO_INSTALL_MODE=standard`：关闭旧绿色包自更新器，避免标准安装与绿色包目录替换机制混用。

## 绿色包迁移与卸载

安装器支持显式参数：

```text
/MIGRATEDIR="旧绿色包目录"
```

普通图形安装流程同时提供“迁移旧版数据”页面。只有用户勾选并选择包含 `VERSION.json` 的目录后才执行迁移；命令行 `/MIGRATEDIR` 继续供 CI 和批量部署使用。

迁移前要求源目录包含 `VERSION.json`。只复制以下白名单数据，不复制旧应用代码或 Python 运行时：

- `config.json`（目标不存在时才复制）
- `查询日志/`、`日志/`、`logs/`
- `运行数据/`、`data/`、`数据/`
- `imports/`、`导入文件/`

目录迁移使用 Windows `robocopy`，不覆盖标准安装目录中已经存在或更新的数据，且不跟随目录联接。源绿色包目录始终只读，不会被安装器删除。

卸载只删除版本目录、标准启动器、快捷方式、协议和卸载注册信息；上述用户数据继续保留在安装根目录。安装目录因此可能在卸载后仍存在，这是有意的数据保护行为。

## `xynigo://` 安全边界

当前允许：

- `xynigo://start`
- `xynigo://wake`
- `xynigo://pair?code=ABCD-EFGH`

`start/wake` 当前不接受任何参数；`pair` 只接受云端五分钟一次性配对码。协议解析拒绝用户名、密码、端口、片段、重复参数、长期凭证以及采购/下单等业务动作。协议只进入本地启动或配对入口，不能绕过云端权限、设备租约和本地任务闸门。

Windows 使用命名互斥量 `Local\XynigoSourcing.Executor` 阻止同一用户重复启动多个执行器实例。

协议现在由已安装的 `Xynigo.exe --protocol` 接收。状态中心自身使用独立单实例互斥；第二次点击快捷方式或协议不会创建第二个托盘进程，只把“显示 / 启动 / 配对”请求转交现有状态中心。一次性配对码只短暂进入本机私有命令文件，消费后立即删除；长期设备凭证仍只进入 Windows CurrentUser DPAPI。

## 状态中心安全状态接口

本地执行器新增回环只读端点 `GET /executor-status.json`。它不依赖云端用户会话，只返回：

- 执行器版本与运行状态；
- 是否完成设备配对、设备显示名和平台；
- 云端通道状态、最近心跳与稳定错误码；
- HubStudio 是否连接；
- 本机任务数量、任务类型标签和耗时。

响应明确排除设备 ID、任务 ID、资源标识、原始 HubStudio 错误、配置值、密码、Cookie、Token 和任何凭证。托盘关闭执行器使用单进程随机控制令牌，且仅接受回环请求。

## Authenticode 真实签名流水线

仓库新增 `packaging/windows/sign-windows-artifacts.ps1` 和手动发布工作流 `.github/workflows/windows-signed-release.yml`：

1. 构建 `Xynigo.exe` 原生状态中心；
2. 使用可信代码签名证书以 SHA-256 签名，并添加 RFC 3161 SHA-256 时间戳；
3. 把已签名启动器嵌入 NSIS 安装器；
4. 再签名安装器；
5. 通过 `signtool verify /pa /all /v` 和 `Get-AuthenticodeSignature` 双重验证 Windows 信任与时间戳；
6. 重新计算签名后 SHA-256，只有验证全部通过才允许把元数据改为 `releaseEligible=true`；
7. 静默安装后再次验证安装目录内 `Xynigo.exe` 的签名，再执行迁移、协议、重装和卸载保留测试。

流水线不支持测试证书或自签名证书冒充正式交付。当前本机证书库、GitHub Actions Secrets 和 Azure Artifact Signing 均没有可用的可信 Windows 签名身份，因此本地开发产物继续保持 `authenticodeSigned=false / releaseEligible=false`，不得上传云端下载入口。

## 云端下载接入

云端 Web 已支持标准安装包展示：安装方式、数字签名发布者、SHA-256、品牌安装步骤和状态中心/托盘说明。防御性门禁规定：

- Windows 标准包必须具有签名、时间戳和发布者元数据；否则不得作为推荐资产；
- macOS 标准包必须同时满足 Developer ID Installer 签名、公证和 stapling；
- 每个平台可以在标准资产旁提供 `greenFallback`。标准包缺失、下载地址不可用或签名门禁未通过时，Web 自动改用绿色包并显示真实文件名、大小、SHA-256 和绿色版启动说明；
- 新版 Windows 绿色包通过 `launcherFile=Xynigo.exe` 声明状态中心入口；旧绿色包没有该字段时，Web 保留原 `启动.bat` 说明，不能误导用户；
- 绿色包不会伪装成标准安装完成，也不会把 SHA-256 完整性校验描述成发布者签名；
- 正式目录只有在新版本签名资产上传不可变 Release、SHA-256 回读并部署对应云端清单后才切换。
