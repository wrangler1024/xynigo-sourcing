# Web 工作台采购中心接口（P0）

日期：2026-08-26

状态：只读接口、采购认领、采购分单测试接口已部署到云端测试实例；2026-08-26 新版采购中心读取契约、采购契约 v2 和店铺/运营独立归属已部署到共享测试环境，迁移为 `0006_purchase_operator`。批量认领列表交互、店铺/运营精确筛选、利润字段和字段可见性投影已在本地完成但尚未部署。业务操作日志 P0 仍只在本地代码完成，未部署。真实资源绑定、下单会话和付款结果写入仍未开放。

## 目标与边界

本批为采购中心 Web 工作台提供概览、采购单列表、详情、采购明细认领和本人采购执行列表。旧版采购分单保存与分单队列接口继续保留兼容，但不再作为新版前端认领后的必经链路。PostgreSQL 继续作为采购业务事实源；飞书 Base 是后续协同镜像，店小秘原生审核和真实平台下单都不是本接口的副作用。

所有接口同时执行：

- 当前飞书会话有效性校验；
- 读取接口校验 `procurement.request.read`，认领与分单写接口校验 `procurement.execution.manage`；
- `tenant_id` 数据库查询隔离；
- `Cache-Control: no-store` 响应策略。

浏览器只访问 Xynigo 本机同源 `/api/procurement/*`，由本机服务携带系统安全存储中的 Bearer 会话代理到云端。Bearer 会话不会返回给浏览器。

## 接口清单

| 用途 | Web 同源接口 | 云端接口 |
|---|---|---|
| 采购概览 | `GET /api/procurement/overview` | `GET /v1/procurement/overview` |
| 采购单列表 | `GET /api/procurement/orders` | `GET /v1/procurement/orders` |
| 采购单详情 | `GET /api/procurement/orders/{purchaseOrderId}` | `GET /v1/procurement/orders/{purchaseOrderId}` |
| 认领采购明细 | `POST /api/procurement/claims` | `POST /v1/procurement/claims` |
| 保存采购分单 | `POST /api/procurement/orders/{purchaseOrderId}/splits` | `POST /v1/procurement/orders/{purchaseOrderId}/splits` |
| 采购执行队列 | `GET /api/procurement/execution/splits` | `GET /v1/procurement/execution/splits` |

本机代理只允许上表路径及对应 HTTP 方法；任意外部 URL、路径穿越、管理接口、非 UUID 详情路径或读写方法错配均拒绝。

## Web 页面实现

采购中心一级入口包含“采购任务”和“采购执行”；“异常协同”继续保持规划状态。新版采购任务页包含：

- 六项可点击概览卡片，直接形成任务范围快捷筛选；
- 默认展示团队公共待认领采购单，支持任务范围、站点、店铺、运营、关键词和每页数量筛选；
- 宽屏采购单列表展示店铺/运营、收件人/国家、销售金额、采购指导额、预估利润、利润率、明细/件数、采购状态、采购员、提交人与最近更新时间；
- 支持当前页逐单勾选、全选和整单批量认领，认领成功后直接刷新并进入当前采购员的采购执行页；
- 列表只返回收件人姓名与国家，电话、邮编和详细地址只在独立采购单详情工作区按权限读取。

新版采购执行页通过 `claimedByMe=true` 直接读取当前账号已认领的采购单，因此没有提前生成分单的采购单也会出现。列表保持宽屏，一行固定只显示“详情”和“处理”两个按钮；“处理”下拉承载继续采购和查单跟单。详情在独立工作区页签展示收件地址、采购备注主/次规格、采购进度及按批次纵向排列的跟单环境。关闭详情页签会清空详情 DOM 和引用。所有端到端测试只使用脱敏合成数据。

## 店铺与运营归属契约

采购契约 v2 保留店小秘传入的完整 `storeName`，并显式增加：

| 字段 | 类型/长度 | 口径 |
|---|---|---|
| `storeBaseName` | string，最多 300 字符 | “店铺名-运营姓名（组别）”中的基础店铺名 |
| `operatorName` | string，最多 100 字符 | 店铺名中的运营姓名 |

例如 `蓝天-周远超（一组）` 解析为 `storeBaseName=蓝天`、`operatorName=周远超`。括号中的运营组别当前只保留在 `storeName` 原文，不拆请求字段、不建数据库列，也不进入统计口径。

`purchase_orders` 同步增加 `store_name varchar(300) not null`、`store_base_name varchar(300) not null`、`operator_name varchar(100) null`。运营字段允许为空只为兼容旧契约和无法识别的历史记录；v2 正式提交必须提供可由店铺原文校验出的基础店铺名和运营姓名。运营统计使用独立列，不再使用提交人别名。旧 v1 请求继续接受，且规范化摘要不增加新字段，避免历史采购单幂等键和内容哈希发生变化。

## 采购单列表

查询参数：

| 参数 | 可选值/范围 | 默认值 |
|---|---|---|
| `submissionStatus` | `draft`、`submitted` | 全部 |
| `syncStatus` | `pending`、`synced`、`failed`、`conflict` | 全部 |
| `workflowStatus` | `draft`、`unclaimed`、`claimed`、`purchasing`、`ordered`、`logistics_filled`、`completed`、`returned`、`exception` | 全部 |
| `taskScope` | `unclaimed`、`processing`、`ordered`、`abnormal` | 全部 |
| `claimedByMe` | `true`、`false` | `false` |
| `site` | 站点代码，如 `US`、`MX` | 全部 |
| `store` | 基础店铺名精确匹配，最长 300 字符 | 全部 |
| `operator` | 运营姓名精确匹配，最长 100 字符 | 全部 |
| `keyword` | 采购单、平台单号、店铺、运营或收件人关键词，最长 200 字符 | 空 |
| `page` | `1..100000` | `1` |
| `pageSize` | `1..300` | `50` |

## 字段数据权限预留

`fieldVisibility` 由服务端鉴权/策略层生成，不是客户端查询参数。当前默认五项全部可见，尚未提供角色配置页面。未来隐藏字段时，服务端必须在返回响应前完成投影：

- 隐藏店铺或运营时同步移除对应筛选选项；隐藏运营时不得回传包含运营姓名的完整店铺展示名；
- `orderKey` 可能包含店铺与运营，任一字段隐藏时一并移除；
- 隐藏销售金额时同时移除销售币种及详情预估指标中的销售额；
- 隐藏利润时同时移除可直接反推利润的预估成本、充值额、ROI 和成本口径；
- 前端按 `fieldVisibility` 调整列和筛选控件只是展示适配，不能替代服务端裁剪。

## 采购单详情

详情在列表摘要基础上增加：

- `schemaVersion`、`contentHash`、`executionRevision`；
- `draft`：不含 `items` 的主单快照，包含收件信息和订单级字段；
- `lines`：有效采购明细，包含 `purchaseOrderLineId`、稳定 `lineKey`、`lineNo`、`workflowStatus`、`claimedBy`、`claimedAt`、`updatedAt` 和 `payload`。
- `executionBatches`：兼容读取已存在的测试分单/采购批次，用于新版详情纵向展示付款成功批次的查单入口；新版前端不会在认领后自动创建这些批次。

详情包含收件信息，因此每次成功读取写入 `purchase_order.workspace.detail.read` 兼容 action，统一操作类型为 `purchase_order.recipient_sensitive.read`；日志保存内部采购单 ID、安全平台单号和“读取了哪些敏感字段”的字段名摘要，不保存电话或地址值。明细从 `draft.items` 中拆出，避免相同商品数据在响应中重复两份。

## 状态口径

- `submissionStatus=draft`：可继续更新的采购草稿。
- `submissionStatus=submitted`：已正式提交并锁定当前内容版本。
- `syncStatus=pending`：Outbox 待处理，不表示飞书 Base 已同步。
- 明细正式提交后初始为 `workflowStatus=unclaimed`。
- 认领后明细进入 `workflowStatus=claimed` 并记录当前采购员与认领时间；重复认领自己的同一明细幂等，已被他人认领或进入后续流程时返回冲突。
- 采购分单保存使用 `executionRevision` 乐观并发控制。当前采购员已认领的有效明细必须全部分配，且各分单数量合计必须等于采购数量。
- 分单未绑定资源时为 `waiting_binding`，绑定完整同站点资源后为 `waiting_order`。
- `purchasing`、`ordered`、`exception` 状态已预留，但本测试版本没有真实下单、平台订单回填、退回、异常处理或飞书同步写接口。

认领测试接口接受采购单 ID 或采购明细 ID。整单与批量只是选择便利，后端最终锁定并更新采购明细；整个请求原子提交，避免同一明细被并发认领。

采购分单数据模型支持同一采购明细按数量分配到多张分单。当前前端测试交互先提供整条明细在分单间移动，后端数量模型已为下一轮“同一行拆数量”交互预留。每张分单可独立绑定同站点的 `Hub 环境 + 买家号`；也可暂不绑定并进入“待绑定资源”。一张采购分单代表一次实际下单上下文。

新版“采购执行”页以采购单为主对象，不以预先生成的分单为入口。状态概览、筛选和宽屏列表全部基于当前账号已认领采购单；列表展示店铺/运营、金额、明细/件数、采购进度、执行状态和当前下单/跟单资源。资源测试数据仍只保存安全引用和脱敏标签；数据库和响应均不保存、接收或回显买家号密码、Cookie、接码 Key 等凭证。

## 错误与验收

- 未登录或会话失效：`401`。
- 缺少 `procurement.request.read`：`403 permission_denied`。
- 缺少 `procurement.execution.manage`：认领和分单保存返回 `403 permission_denied`。
- 采购单不存在或属于其他租户：`404 purchase_order_not_found`。
- 非法筛选值、页码或非 UUID 详情 ID：`422`。
- 认领冲突：`409 purchase_line_claim_conflict`。
- 分单版本冲突：`409 purchase_execution_revision_conflict`。
- 分单数量不完整：`422 purchase_split_quantity_mismatch` 或 `purchase_split_allocation_incomplete`。

合成测试覆盖租户隔离、权限拒绝、概览聚合、快捷任务范围、站点/关键词筛选、当前采购员执行列表、列表敏感字段最小化、详情审计、认领幂等、数量拆分、资源安全标签、乐观锁冲突、销售订单号搜索和本机代理路径/方法白名单。

| 采购行为 | 兼容 action | 统一 operationType |
|---|---|---|
| 采购单提交 | `purchase_order.submit` | `purchase_order.submit` |
| 采购明细认领 | `purchase_order.lines.claim` | `purchase_order.claim` |
