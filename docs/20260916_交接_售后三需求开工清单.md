### 部署注意（真机验证过两次的坑）

- `0039` 是迁移：`sudo docker compose run --rm migrate` **不会自动重建镜像**，必须先 `sudo docker compose build migrate`，否则报 `Can't locate revision ...`（极易误判成代码问题）。
- 部署流程按 `docs/部署与发布手册.md`：预检 `df -h /` → 等在途任务排空（**二次采样确认 0**，不把一次零采样当排空）→ 旧镜像打 tag + `pg_dump -Fc` 备份 → rsync → `build migrate` + `run --rm migrate` → 核对 `alembic_version` → `build auth` + `up -d` → 逐项核验。

### 口径要点（避免走偏，逐条都在文档里）

1. **补提失败的范围＝可恢复失败**：`fail` / `login` / `inuse` / `stopped`；**排除 `blocked`**（平台判定已无可退包裹，重提只会白跑一遍写操作，界面不给入口）。写操作 → 二次确认。
2. **共用同一个建 Run 入口**：补提失败、直接提交指定单、提交历史里的重提，三者共用一条提交路径，**不要写第二条**。
3. **提交历史按单批次（run）成行**，不做 root run 合并视图；重提产生新批次，用审计 `change_summary` 记「重提自哪一批」（倾向不加列、不加迁移）。
4. **列表默认互相可见**（租户内全可见）——**刻意偏离**物流查询/创建环境的既有口径（那两处是「本人 + 管理员看全租户」）。实现时**不要照抄 `history_admin` 那段过滤**；审计照常记操作人。
5. **可照抄的现成形态**：物流 `GET /v1/operation-runs/logistics-query/history`（`main.py:4659`）+ `.../history/{root_run_id}`（4722）；建环境同构在 `4038`/`4095`；Web 弹层用 `environmentHistory*` 那套；**「从历史发起动作」的先例＝建环境详情里的 `loadInterruptedEnvironment()`（index.html:10391 续跑）**。
6. **批次导出复用 ④ 导出口径**：`after_sale_export.py`（表头样式、空值留空不写「—」、商品图列写 CDN 链接不内嵌）。
7. 从历史发起回访＝把该批次**有退款单号的行走**灌进 ④，**不新增第二条回访路径**。
