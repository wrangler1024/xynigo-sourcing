## 问题与结果

旧扫描优先进入已发货分类，只将有丢件退款入口的卡片作为主结果；没有入口时补扫其他分类，
并把 skip 显示成“无订单”。现场只读核对的三个环境实际都有运输中的订单，当前没有丢件退款入口。
业务订单标识与环境定位不写入工程仓。

现在从 `status_type=0` 的所有订单页开始，等待列表就绪，按下一页读取并按订单号去重。
已读到的订单全部保留；仅有丢件退款入口的订单调用既有只读 pre_info 核验。
无入口的运输中、备货中、已送达、退款中、已退款等订单按卡片状态解释，不能据缺入口推断申请窗口已过。
只有列表明确显示空态才返回 empty；加载、翻页或可申请性核验失败显示失败。

每个订单的状态和说明由本地桥接投影到已有 status/errorSummary 字段，未增加跨端必填字段或数据库列。
保留订单卡片商品图作为无可退包裹时的图片来源。Web 兼容旧执行器的有订单号 skip/empty 行，显示“暂不可申请”。
同时修复扫描终态回执把可申请订单数限制为不超过环境数的问题；计数仍必须与实际可申请行数一致。

## 正样本复核与扫描加固（第二轮）

追加的三个授权现场环境均在所有订单页显示送达标记及丢件退款入口。
只读 pre_info 均返回业务成功码 0、退款理由 83、1 个可退包裹、0 个不可退包裹。
加固后的实际扫描实现逐环境复查，三单均得到 `status=ok / claimable=true / packageCount=1`，
并读到送达时间及订单金额；没有提交退款。

现场确认的两个边界：已送达卡片的通用状态仍可显示 Enviado；送达日期可能晚于售后入口渲染。
因此扫描不按 Enviado 排除候选，单独读取物流送达标记与日期，并对延迟日期有限等待。
日期持续缺失不妨碍有入口订单的可申请性核验。重复卡片去重时保留已发现的入口和展示字段，
仍重新请求平台核验，不能因旧卡片有入口直接认定可申请。

扫描增加专用严格核验路径，不改变既有退款提交链：

- HTTP 或业务错误、理由不是 83、缺失/异常包裹列表、缺失包裹标识、包裹重复或可退/不可退冲突，
  均报告核验失败，不按“无可退包裹”处理。
- 每单只读请求独立编号和状态对象；迟到响应不能覆盖下一单。结束或超时清理状态并中止未完成请求。
- 页面离开预期站点时不发出查询；订单卡片无法识别时明确失败，不静默漏掉。
- 新增脱敏回归位于 `tests/test_after_sale_scan_all_orders.py` 与 `tests/test_after_sale_scan_pre_info.py`，
  包括真实形态抽象、日期缺失、重复卡片、响应异常、迟到响应隔离、清理与错误站点阻断。
- 第二轮本地全量：1103 passed / 5 skipped；公开源码安全审计与 diff 检查通过。
  云端代码与字段契约本轮未变，未重复运行云端套件；首轮售后/导出专项 21 项通过记录仍保留在上节。

## 限制与后续

- 两轮现场样本覆盖三个运输中负样本和三个已送达可申请正样本；真实正样本均为单可退包裹，
  不据此宣称所有平台状态、多包裹或所有分页场景均已实测。
