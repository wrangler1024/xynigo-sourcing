### 第三增量（已完成：前端接线）

| 模块 | 内容 |
|---|---|

### 第四增量（已完成：定时调度）

| 模块 | 内容 |
|---|---|
| `SheinSettlementSyncWorker` | **每 6 小时**对到期租户跑一轮同步；线程 + stop 事件，与仓内既有 worker（feishu_operation_sync / purchase_sync）同构 |
| **到期才跑** | 以该租户最近一次成功/部分成功的同步时间为准，未到间隔就跳过 → **容器重启不会重复同步**，多进程/重复调度也不会多打平台 |
| **同店互斥** | 手动刷新与定时任务共用同一个闸门：`run()` 开跑前检查是否有进行中的同步，有则抛 `SheinSettlementSyncBusy`（接口返回 **409**，worker 安静跳过不记失败） |
| **中断恢复** | 进程被杀会留下 `running` 记录；超过 `stale` 阈值（默认 2 小时）的记录会被标记为 `failed`，不会永久占住闸门 |
| **单租户隔离** | 循环内逐租户兜异常，一家异常不影响其他租户，也不会让 worker 线程退出 |

**配置**（环境变量，默认关闭以免部署即对外打网关）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `XYNIGO_AUTH_SETTLEMENT_SYNC_ENABLED` | `false` | 开启定时同步 |
| `XYNIGO_AUTH_SETTLEMENT_SYNC_INTERVAL_SECONDS` | `21600`（6 小时） | 同步间隔，下限 60 秒 |
| `XYNIGO_AUTH_SETTLEMENT_SYNC_STALE_SECONDS` | `7200`（2 小时） | 超过此时长仍 running 视为异常中断，可被接管 |

### 三轮评审整改（20260917，结论「改后合并」）

| # | 三轮问题 | 处理 |
|---|---|---|
| 1 | **失败快照被当成订单水位**：失败快照写在 SAVEPOINT 外、`synced_at` 是本轮 now，而本轮拉到的台账更新已被回滚。拿它当水位会把 `[上次成功, 本轮−重叠]` 整段窗口跳过 → 期间签收/新发货再也不会出现，在途长期偏离 | 水位**只认 `status == "ok"` 的快照** |

建议项一并处理：**空店（台账 0 行）也接受成功快照水位**（否则从未出过单的店每轮都走 60 天全量回溯）、
**`incomeExpenditureType` 缺失/非法即整店失败**（原 `int(x or 1)` 会把 0/None 当成收入，支出被算成正数→轧差错）、
**导出打款日列也按状态留空**、**报账单假网关改真分页**（原先第 1 页回全部，「200 页上限」这条路径测不到）。

**⚠️ 本轮我自己写的回归位也出现过一次假绿**：失败轮的水位用例第一版把 T2 取在"距上次成功 1 小时"处，
而增量窗有 2 小时重叠 → 被跳过的区间是空集，**修与不修都是绿的**。改成"失败轮距上次成功 > 2 小时、
且更新落在被跳过区间"后才真正生效（已验证：去掉修复该用例变红、在途虚高 88.80）。这与评审反复指出的
「测试看着在测、实际走不到」是同一类，值得作为方法教训记下：**构造边界用例时要先验证它在缺陷下确实失败。**

## 1. 背景与目标

业务背景：公司需要监控 SHEIN 项目的资金周转情况——钱当前压在哪一段（在途 / 待结算 / 已结算）、多久回一次款、下一笔什么时候到。

现状与痛点：

- 现行「小犀助手 › 店铺结算查询」由执行器打开 HubStudio 环境、自动登录卖家后台采集结算数据（只读），导出《店铺结算汇总表》交财务。
- 该链路依赖每个环境的**账号 + 密码 + 接码链接**三件套，单店分钟级（含登录、短信 OTP、密码二次验证），需人工发起，本质是"每周或按需"的批量动作，**不是实时基准**。
- 环境占用、接码失效、登录风控任一环节不稳就会缺店，且采集结果是页面汇总数字，无法逐单追溯。

本期目标：改为**纯云端接口方案**——无浏览器、无执行器、无接码、无环境占用；多店汇总；可定时与随时刷新；数据可逐单追溯到订单号。

## 2. 方案选择：为什么放弃巡检自动化

| 维度 | 巡检自动化（现状） | 开放平台接口（本期） |
|---|---|---|
| 依赖 | HubStudio 环境 + 账密 + 接码链接 + 执行器在线 | 云端服务器 + 已授权店铺凭证 |
| 触发方式 | 人工发起 | 可定时、可随时刷新 |
| 单店耗时 | 分钟级（登录 + OTP + 二次验证） | 秒级（纯 HTTP） |
| 稳定性风险 | 登录态、风控、接码平台、环境占用 | 接口权限、IP 白名单、限流 |
| 数据粒度 | 后台页面汇总数字 | 逐单 + 逐账单（可对账到订单号） |
| 历史留存 | 导出文件 | 可落库形成时间序列 |

**结论**：结算看板走纯接口。巡检模块**保留不动**（定位见 §7）。

## 3. 数据层：已实测的接口口径

以下全部基于 20260917 生产环境真机实测（非文档推断）。

### 3.1 接口清单

| # | 用途 | 接口 | 关键入参 | 关键返回 |
|---|---|---|---|---|
| 1 | 报账单（已结算 / 待付款） | `POST /open-api/finance/report-order-list` | `page/pageSize`（整数）、`reportStatus`、打款时间 | `reportStatus`(1 即将付款 / 2 已付款 / 3 付款异常)、`income`、币种、`paymentMethod`(1 直接打款 / 2 钱包充值)、收款账户 |
| 2 | 对账单（待结算 / 下次打款） | `POST /open-api/finance/get-check-order-list` | `page/pageSize`(≤30)、`startAddTime/endAddTime`（对账单**生成时间**，窗口 **≤7 天整**）、`checkStatus`、`bzOrderNos`(≤100) | `estimateIncomeMoneyTotal` 应付金额汇总、**`estimatePayTime` 预计打款日期**、`checkStatus`、`reportOrderNo`、**`bzOrderNo`（业务单号=订单号，可逐单追溯）**、`incomeExpenditureType`(1 收入 / 2 支出) |
| 3 | 订单列表 | `POST /open-api/order/order-list` | `queryType`(1 下单 / 2 更新时间)、`startTime/endTime`(UTC+8，窗口 **≤48h**)、`page/pageSize`(≤30)、`orderStatus` | 只返回单号、状态、时间 |
| 4 | 订单详情 | `POST /open-api/order/order-detail` | `orderNoList`(≤30) | `estimatedGrossIncome` 预计收入 等金额字段 |
| 5 | 报账单销售款明细 | `POST /open-api/finance/report-sales-detail` | — | **当前应用无权限（403）**；**已找到替代路径，见 #6** |
| 6 | **对账单详情（逐 SKU 费用拆分）** | `GET /open-api/finance/get-check-order-detail` | `checkOrderNo`（对账单号，取自 #2） | `itemList` **逐 SKU 明细**，含 `incomeAmount` 预计收入、`commissionAmount/Rate` 佣金、`serviceFee` 服务费、`performanceCost` 履约服务费、`returnExpense` 退货处理费、`returnFreightSubsidy` 退货运费补贴、`stockExpense` 备货作业费、`couponAmount` 优惠券、`sellerRealTax` 欧洲 VAT、`saleTax` 买家消费税、`costPrice` 供货价（半托管）、`subjectAmountList` 税费明细（MX 代扣代缴 WHT_VAT/WHT_IT 等）、`refundRatio` 退款比例；另有 `originalOrderNo` 原始订单号、`secondOrderType` 二级账单类型、`site` 销售站点 |
| 7 | 报账单补扣款收支明细 | `POST /open-api/finance/report-adjustment-detail` | — | 补扣款（非销售款）的收支明细 |
| 8 | 店铺站点与币种 | `GET /goods/query-site-list`（旧：`/openapi-business-backend/site/query`） | — | 店铺站点与**站点币种**——币种口径的权威来源 |

补充事实：

- 财务域另有旧版报账单列表（未授权路径）与补扣款接口；文档目录中的 `report-list` 是旧版，实际可用的是 `report-order-list`。
- **接口权限 ≠ 应用审核**：控制台 API 权限包「自运营&半托管对账单管理」覆盖 #1 与 #2，**#6 对账单详情按权限包名称（…get-check-order-list/detail）应同属该包**，联调首日需实测确认。
- `orderStatus` 取值：1 待处理 / 2 待发货 / 3 待 SHEIN 发货 / **4 已发货** / 5 已签收 / 6 已退款 / 7 待揽收 / 8 已报损 / 9 已拒收。
- 订单金额口径：`estimatedGrossIncome` = `productTotalPrice` − 活动优惠 − `totalCommission`；平台代收税（如墨西哥 `totalMxTaxPrice`）不进结算，已验证。
- **限流按接口不同**：报账单列表（#1）文档明确为 **20 次/秒**；订单类为 100 次/秒。多店并发前按各接口上限分别设闸门。

### 3.2 指标定义（Jeff 20260917 定稿口径）

| 看板指标 | 口径 | 数据来源 |
|---|---|---|
| **在途资金** | Σ `estimatedGrossIncome`，条件 `orderStatus=4`（已发货未签收） | 订单列表 + 订单详情 |
| **待结算资金** | 对账单 `checkStatus=1` 按**收支轧差**净额（收入 − 支出） | 对账单 |
| **下次结算金额** | 同源净额中**仅最近一个打款日（`estimatePayTime` 最小值）那一批**；下方按打款日逐批列明 | 对账单 |
| **预计打款日** | `estimatePayTime`（**逐批**，同一店铺可有多个） | 对账单 |
| **已结算资金** | 报账单 `reportStatus=2` 聚合 `income`，**历史全量累计**（非本期、非本年度） | 报账单 |

**呈现口径**：四个指标均按「人民币合计 + 各币种原币金额」双层呈现（Jeff 二次拍板，见 §9 #10）。人民币合计 = 各币种原币金额 × 维护汇率后求和；**店铺明细表保持原币口径**，作为可与平台后台逐单回溯的核对底稿，不参与折算展示。

#### ⚠️ 打款日不对齐时的汇总规则（关键，易错）

`estimatePayTime` 是**逐单/逐批**的，各店铺的打款日并不一致（实测同一店铺自身就会有两批：如 09-21 / 09-28）。因此**「把所有待结算金额加起来、配一个最早打款日」是错的**——那等于告诉财务这些钱都在那天到账，实际是分批到。正确做法：

1. **按 `estimatePayTime` 分组求和**：每个打款日一个批次，批内再按币种拆分，批次按日期升序。
2. **「待结算资金」= 全部 `checkStatus=1` 净额**（不按日期切分，回答"一共有多少钱没结"）。
3. **「下次结算金额」= 仅最近一个打款日那一批**（回答"下一笔到多少"）。
   - 若两者都取全量，会是同一个数——这是必须避免的口径重叠。
4. **页面上不做全量排期铺开**（Jeff 20260917 反馈：把未来所有结算日期都统计出来会让页面很乱）：
   - 卡片「下次结算金额」**只呈现最近一批**：人民币合计 + 该批各币种原币 + 一行「预计打款 YYYY-MM-DD」；**不列后续批次**。
   - 明细表「预计打款日」列**只放最近一个打款日**；该店还有后续批次时附「+N 批」小标（如 `2026-09-21 +1 批`），保留"还有后续"的信息但不撑乱列宽。
   - **完整排期只在导出文件的「结算排期」区块**（打款日 / 该批折人民币 / 该批各币种原币），需要按到账日排资金计划时查文件，不占页面。
5. 导出中单列**「结算排期」区块**（打款日 / 该批折人民币 / 该批各币种原币），供财务按到账日排资金计划。

**校验恒等式**：各批次金额之和 ≡ 待结算资金总额（可复算，原型已按此校验通过）。

三条口径的实测关系（已验证，是本看板的正确性基础）：

1. **逐单可对齐**：同一订单在订单侧的 `estimatedGrossIncome` 与对账单收入行金额分毫不差——两套数据同源，可交叉校验。
2. **待结算 ⊇ 待付款**：对账单（`checkStatus=1`）覆盖报账单（`reportStatus=1`）。差额 = 已生成对账单但未进打款队列的部分（实测出现过账单级待付款为 0、而对账单待结算仍有值的情形）。因此**主口径取对账单**，账单级报账单不能单独代表"待结算"。
3. **订单级聚合会高估**：对账单的支出行（退款 / 调整，`incomeExpenditureType=2`）只在结算侧出现，订单侧金额不回更。所以纯订单级求和偏高，**必须以对账单轧差修正**——这个差额本身就是结算调整告警点。
4. 另实测：某店 14 天内在途为 0，说明在途是波动量而非常态存量，看板需要保留历史快照才能看出周转。

### 3.3 与现行巡检六列的覆盖度

现行《店铺结算汇总表》六列 vs 纯接口方案：

| 巡检列（现行交财务口径） | 纯接口可否覆盖 | 来源 |
|---|---|---|
| 在途订单金额 | ✅ | 订单级 `orderStatus=4` |
| 累计未结算金额 | ✅ | 对账单 `checkStatus=1` 净额 |
| 下次结算金额 | ✅ | 同上 + `estimatePayTime` |
| 已完成结算收入 | ✅ | 报账单 `reportStatus=2` |
| **不可提现金额** | ❌ **接口侧无对应** | — |
| （巡检已采但未进六列）可提现 / 提现中 / 资金限制 | ❌ 同上 | — |

⚠️ **口径差异需注意**：巡检六列中的「已完成结算收入」取自卖家后台卡片的**本年度已结算金额**（年度切片）；而财务本次要的是**历史总结算资金**（全量累计）。两者不是同一个数，看板按后者实现。差异原因（原先口径不准 / 财务口径调整）建议与财务再确认一次，避免两张表对不上。

**这是纯接口方案最明确的取舍点**：开放平台财务域只有报账单、销售款明细、补扣款、对账单这几类接口，**没有资金账户与提现类接口**。「不可提现 / 可提现 / 提现中 / 资金限制」来自卖家后台「我的资金管理」页，接口取不到。纯接口方案覆盖巡检六列中的 4 列，但粒度更细（可到订单号）。

#### 商家钱包能力核实结论（20260917 查开放平台文档站全量接口目录）

**结论：开放平台财务与订单接口不返回商家钱包数据（余额 / 可提现 / 提现中 / 不可提现 / 资金限制均无接口）。**

核实口径：文档站侧栏全量 **233 个接口 / 36 个接口域**逐一枚举，`finance` 域**恰好 6 个**（报账单列表新旧 2 + 销售款收支明细 + 补扣款收支明细 + 对账单列表 + 对账单详情），无钱包/资金账户/余额/提现类接口；对全部接口名做宽口径关键词扫描（钱包、资金、余额、提现、账户、资产、银行、收款、打款、付款、回款、授信、余额等）亦无命中（命中的「发品额度 / 上架额度」是发品配额，不是资金）。

**但平台侧确实存在「商家钱包」概念，只是接口只暴露标记、不暴露余额**：

| 报账单字段 | 含义 |
|---|---|
| `paymentMethod` | 收款方式：**1 直接打款 / 2 钱包充值** |
| `completedPayTime` | 打款日期；**收款方式为「钱包充值」时返回充值到账时间，为「直接打款」时返回付款完成时间**（与商家后台展示一致） |
| `rxAcct` | 收款账户 |

⚠️ **这对「资金周转监控」是一条实质口径差异**：`reportStatus=2`（已结算）对**钱包充值**店铺只代表钱进了 SHEIN 平台钱包、尚未进入公司银行账户，与直接打款店铺的「已结算」在现金可用性上不等价。建议看板在店铺维度保留 `paymentMethod`（直接打款 / 钱包充值）与收款账户，并在汇总口径说明中提示——否则「已结算资金」会被误读为已到账可支配资金。**（待确认：本批店铺实际走哪种收款方式；若存在钱包充值店，是否需要在卡片上单列一行）**

## 4. 工程约束与解法

### 4.1 拉取窗口限制（最需要提前设计的一点）

- **订单列表窗口 ≤48h 且 `pageSize`≤30**：无法一次拉全"所有已发货未签收"。一张 5 天前发货、至今未签收的订单，若 48h 内没有更新时间，就不会出现在窗口里 → 直接查会**漏计在途**。
- **对账单窗口 ≤7 天整**，毫秒越界直接报错（`gsfs99401`）。

建议解法：

- **订单侧建本地状态台账**：首次按 48h 分片向前回溯（回溯到无 `orderStatus=4` 单为止，并设最大回溯天数上限兜底）；此后每次刷新只拉 48h 增量并 upsert 本地表；**在途 = 本地表中 `orderStatus=4` 的金额合计**。这样避免每次全量回溯，也避免漏单。
- **对账单按 7 天分片**，边界取整秒；常规刷新只需覆盖最近 1–2 个窗口，再按 `checkStatus` 过滤。
- **历史累计已结算按打款时间分片全量回填**：财务要的是历史总结算资金（全量累计），不是本年度，因此首次同步需要把该店 `reportStatus=2` 的全部历史报账单翻完再求和，之后只增量追加。回填结果落本地累计表，避免每次刷新重算全量。
  - ⚠️ **待真机确认**：`report-order-list` 是否强制时间窗、单次最大回溯跨度是多少。若与对账单一样限制窗口，则首次回填需按窗口逐段走，单店调用量随经营时长线性增长——这直接决定首次同步耗时与是否需要断点续跑。
- 分页每页 ≤30，逐页拉到取完。

### 4.2 调用规模与限流

- 在途金额需要逐批调订单详情（≤30 单/次），调用次数由单店在途单量决定。
- 平台限流：订单类 100 次/秒，但**同一应用跨店共享**，建议设置全局并发闸门 + 指数退避重试，避免多店同时刷新打满。
- 先做串行/小并发，跑通后按实测耗时再放宽。

### 4.3 出口 IP 白名单

生产接口校验调用方 IP。**测试机与生产机 IP 已加入平台白名单**（沿用店铺授权模块的部署结论），云端直连即可，**不需要执行器参与**。

### 4.4 刷新形态（已定：每 6 小时 + 手动）

- **每 6 小时自动同步一次**（云端定时调接口取数并落快照），页面同时保留**手动同步**按钮给"现在就要看"的场景。
- 状态条展示「数据时间」「每 6 小时自动同步 · 下次 <时间>」，让人一眼知道数据新旧与下次更新点。
- 6 小时粒度对资金视图足够：SHEIN 结算按批次（实测预计打款日按周历日出，如 09-21 / 09-28），不分钟级变化。
- 需注意的实现点：
  - **并发保护**：手动刷新与定时任务可能撞车，同一店铺不得并行同步（沿用既有幂等键思路）。
  - **在途口径依赖订单状态台账**，定时任务要推进台账增量，不能只跑对账单。
  - 首次建台账（全量回溯）耗时较长 → 沿用既有 Run / 任务进度模式（异步任务 + 进度条），不阻塞页面。

## 5. 页面设计（初稿，待原型确认）

入口：**财务中心 › 对账结算**。该二级菜单已存在（当前为 `disabled` 的「规划」占位，权限点 `finance.access` 已预留），本模块将其启用并落地。

结构：

**页面工具栏**（跨区共用）：币种筛选、导出 Excel、刷新数据（手动同步）；并标注数据时间、自动同步间隔与下次同步时间、覆盖店铺数（成功 N / 总数 M）。

1. **汇总区**
   - 四张卡片：在途资金 / 待结算资金 / 下次结算金额（含预计打款日）/ 已结算资金
   - 「已结算资金」按财务口径取**历史总结算资金**（累计），不展示本期/本年度切片
   - 每张卡片**主显人民币合计**（按维护汇率折算），下方以虚线分隔列出**各币种原币金额**
   - 「下次结算金额」卡片**只算最近一批**，并在金额下标注「预计打款 YYYY-MM-DD」；后续批次不上卡片（排期见导出）

   - 列：店铺 · 类型（自营/半托管）· 币种 · 在途 · 待结算 · 下次结算 · 预计打款日 · 已结算（历史累计）· 数据时间 · 状态
   - 支持排序、筛选、翻页（沿用既有 `procurement-pagination` 分页）
   - **每页条数可设 10 / 30 / 50**（沿用店铺授权模块先例）；切换后回到第 1 页，选择持久化到本机（`xynigo.settleDashboard.pageSize`）
3. **对账异常与失败区**
   - **同步失败**的店铺与具体原因（凭证失效 / 无权限 / 限流 / 窗口越界）——**已交付**
   - 订单级聚合 vs 对账单净额的差额告警——**未交付**：前端已有 `kind=diff` 区块可渲染，
     但**同步层尚未计算该差额**（属 §8 P1）。当前看板只会出现 `sync_fail` 一类告警，
     验收与对外说明不得把它写成已交付。
4. **导出 Excel**
   - 导出范围为**当前币种筛选下的全部店铺**（不是当前页），失败行保留并标注状态、金额留空
   - 末尾附汇总块：各币种原币金额 + **末行按维护汇率折算的人民币合计**，并记录数据时间、覆盖店铺数、自动同步间隔与当日汇率
   - 列序：店铺 · 类型 · 币种 · 在途资金 · 待结算资金 · 下次结算 · 预计打款日 · 已结算（历史累计）· 数据时间 · 状态 · 说明
   - 金额汇总一律落到分（两位小数）：浮点累加会把 `29547.730000000003` 这类脏数写进单元格，页面显示被千分位格式化掩盖、导出不会
   - 正式实现沿用仓内先例（巡检 `store_finance_export.py`）由云端生成 xlsx；静态原型阶段由前端生成 CSV（UTF-8 BOM）供口径确认

### 汇率来源与维护方式（Jeff 20260917 拍板：中国银行当日汇率）

| 项 | 结论 |
|---|---|
| **汇率来源** | **中国银行当日汇率**（Jeff 拍板）。实现层需定具体取数入口——中行官网只有展示页、无公开 API，取数方式（页面解析 / 中间数据源 / 财务手工录入）在开发时确认，但**口径是中行牌价** |
| **更新频率** | 当日汇率 → 每次同步取当天值；同一天内多次同步沿用同一值 |
| **是否随快照留存** | **必须留存**：每天的人民币值按当天汇率固化写入快照。否则回看历史时用今天的汇率重算，历史值每次都在变，跨日趋势失去可比性 |
| **精度与舍入** | 先算总额再落到分（避免逐店舍入累积偏差）；金额一律 Decimal |

**取数实现注意**：中行牌价有「现汇买入价 / 现钞买入价 / 卖出价 / 中行折算价」多个口径，**用哪一个需财务指定**（折算记账通常用中行折算价或现汇买入价）。取不到汇率时人民币合计显示「—」，**不得按 1:1 静默计入**。

原型目前用**示例汇率**（1 MXN = 0.3915 CNY、1 USD = 7.1080 CNY，标注日期），仅用于确认呈现形态；真实值接入中行汇率后替换。

### 商家钱包口径（Jeff 20260917：先不关注）

真机已确认首店报账单 `paymentMethod = 2`（**钱包充值**），即回款进 SHEIN 平台钱包而非直接打款到公司银行账户——「已结算」的现金可用性口径与直接打款店不等价。**Jeff 决定本期先不关注**：看板不区分收款方式、不做钱包余额相关呈现。相关字段（`paymentMethod` / `rxAcct`）仍随快照留存，后续需要时可回溯。
