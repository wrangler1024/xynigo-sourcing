# 部署与发布手册

状态：v1 草案 · 20260910，待联合评审和目标环境演练。本文件提供公开流程与现有命令入口，不含服务器地址、内部链接、凭证或生产参数，也不构成任何环境的操作授权。

目标定位、Compose 项目/文件、备份目录、镜像版本和授权依据由发布负责人从私有运维记录核实。下列命令片段须在已确认的目标和配置上下文中使用，不能直接把仓库默认配置当成当前服务器配置。

## 1. 授权与操作范围

| 操作 | 执行边界 |
|---|---|
| 核验版本、健康状态、脱敏日志 | 在任务范围内直接执行；无需部署备份 |
| 本地构建、独立临时数据库迁移验证 | 在开发任务范围内执行，使用合成数据 |
| 共享测试库迁移、服务重启/切换 | 需本次明确授权或覆盖该目标和动作的持续授权 |
| 发布 tag/Release、分发资产、修改自动更新入口 | 需覆盖对应版本、渠道和影响范围的发布授权 |
| 真实平台写入、删除或不可逆数据变更 | 需覆盖具体对象和影响的明确授权 |

同一任务授权可以覆盖备份、迁移、切换、验证和约定的回退，不按命令重复询问。扩大环境、分发范围、数据影响或出现超出约定的风险时，先报告变化；可独立完成的候选准备与检查继续进行。

测试与生产必须独立配置、数据库、卷、网络、密钥和备份，不复制测试数据作为生产初始化。共享服务器上不得顺带修改其他项目。测试环境名称不意味着可以忽略正在执行的业务任务。

## 2. 固定候选并准备变更记录

部署记录至少包含：授权范围、当前环境及版本、候选提交/镜像、目标迁移 head、受影响服务、是否更新桌面资产、兼容性、预期停机、任务保护方式、回退触发条件及负责人。

在干净候选 worktree 中完成相关测试、公开安全检查和生成物检查。确认必需 CI 对应候选提交并实际通过。代码和文档已经提交不等于已部署；旧 CI 结果不证明新候选。

变更前核对当前部署版本、`alembic current` 和候选 `alembic heads`。命令必须使用 `cloud/auth-service` 配置上下文及对应镜像。部署前记录“当前 head → 候选 head”，有迁移时两者可以不同；部署后才要求数据库与候选 head 一致。意外分叉或未知迁移先查明，不直接执行升级。

预构建候选镜像可以在任务排空之前完成，但不得因此启动连接共享数据库的第二个导入 worker。

## 3. 备份与可恢复性

修改共享环境状态前备份 PostgreSQL 和当前实际运行代码/镜像版本；配置与必要密钥的恢复材料通过既有私有安全机制保存，不输出到终端或放入源码、PR、公开资产。备份目录限制访问，避免把业务数据落入普通日志。

数据库备份使用现有 Compose 的 `db` 服务及其容器内环境变量，使用 custom 格式 `pg_dump -Fc`。备份命令必须检查退出状态、文件非空及归档目录可读；原始路径和哈希保存在私有部署记录。

`pg_restore --list` 只能证明归档结构可读，不能代替恢复验证。首次部署、备份方式改变或迁移有数据风险时，在隔离库做恢复演练；日常发布记录最近成功恢复证据和本次结构检查。备份失败或找不到可用恢复路径时停止切换。

代码备份记录实际运行的镜像标识、源码提交/归档和资产清单；只备份本机 HEAD 不能证明旧服务可恢复。不执行删除卷、重建数据库或用备份覆盖当前库的例行“清理”。

## 4. 在途任务保护

### 云端导入 worker

当前 `ProcurementImportWorker.start()` 调用 `_recover()`，会把 queued 以外的未结束导入任务重新置为 queued。不能默认新旧实例并行运行安全。

通过已验证的方式停止接收新导入，等待现有任务结束，并再次核验无在途导入，随后停止旧 worker、启动新实例。若没有可靠的停止接收措施，先制定受控停入或停机方案；不能把一次“任务数为零”采样当成已经排空。

任务仍在写外部系统时，不以重启作为默认修复。不能确认写入是否完成的任务先核对外部结果和幂等条件；不得手动改 queued、清状态或重放来掩盖不确定结果。

### 本地执行器任务与租约

云端服务切换会影响领取、续租和结果回传，但不等于本地动作已经停止。优先等待任务安全窗口；确需带任务切换时，需有经验证的兼容方案、明确租约余量、预期切换时长和超时处置，并在授权范围内执行。

切换前后记录任务状态、进度、attempt 和租约是否连续；不能只核验网页健康。已开始的写任务进入 uncertain 后，不直接重派或删除审计记录，先按恢复流程确认实际结果。

当前没有在本文中假定存在“全局暂停任务”的 CLI/API；具体停入与排空入口需要部署前核实，并作为演练验收项。

## 5. 迁移与切换

审查迁移是否与旧代码兼容。仅当兼容时，采用“备份 → 候选迁移 → 切换 auth”。删除字段、改变语义等不兼容迁移，需采用分阶段兼容或经批准的停机方案，不能机械执行旧顺序。

现有 [compose.yaml](../cloud/auth-service/compose.yaml) 有 `db`、`migrate`、`auth` 服务，`migrate` 默认执行 `alembic upgrade head`。使用已核实的 Compose 项目、配置和候选镜像执行迁移，记录退出状态与 head；迁移失败时停止，不继续切换。

切换仅针对获授权的应用服务及必要资产。不得用整个 Compose 栈的销毁/重建代替应用更新，不重建或复制数据库卷。旧实例完全退出后才启动新导入 worker；不要临时增加副本数来实现未经验证的无停机发布。

远程执行脚本先传成文件再运行，避免 `bash -s` 与 `docker compose exec -T` 争用标准输入。检查完成标记和实际结果，退出码 0 本身不是部署完成证据。

## 6. 部署后验证与回退

| 核验项 | 通过标准 |
|---|---|
| 公网页面 | 实际页面标题/版本及关键变更符合候选，排除旧缓存 |
| `/healthz`、`/readyz` | 返回成功，且服务实际就绪 |
| 应用运行状态 | 运行目标镜像/提交，无持续重启 |
| 数据库迁移 | current 与候选唯一 head 一致 |
| 启动与请求 | 本次窗口无新增启动错误；异常 HTTP 5xx 已解释和处置 |
| 任务连续性 | 导入无意外重排/重写；执行器任务及租约符合切换方案 |
| 安装资产（涉及时） | 容器内实际文件与发布目录的 runtime ID、SHA-256、大小相符 |
| 业务冒烟 | 授权范围内验证关键路径；默认只读或合成数据 |

失败时停止扩大分发，按事先约定回退应用或修复。仅当旧应用兼容当前数据库时才直接切回；数据库恢复可能丢失备份后的写入，须单独评估与授权，不能当作应用回退的默认附带动作。

验证通过后恢复接收任务，记录核验时间、实际部署版本、备份与回退证据。部署完成与业务验收分别记录，外部系统受理不等于业务最终成功。

## 7. 桌面包与跨仓发布

标准桌面发布沿用两段提交：

1. 提交代码、版本号和说明，从该干净源码提交构建双平台候选，保留来源 SHA 和 runtime ID。
2. 校验实际资产，将 runtime ID、SHA-256、大小回填 `cloud/auth-service/src/xynigo_auth/local_executor_release.py`，形成发布元数据提交；复核该提交后在其上打不可变 tag。

构建来源 SHA 与发布 SHA 可以不同，必须分别记录。若第二段包含实际业务代码变化，应重新判断并重建受影响资产，不能仍宣称全部来自已验证源码。未改桌面运行时的云端修复说明桌面资产沿用关系，不强制无意义重建。

Windows/macOS 构建脚本会写共享更新 manifest；同一输出目录顺序构建。并行构建仅可使用独立输出，在受控汇总时验证清单，不允许互相覆盖。发布必须核对签名、公证、测试/稳定通道和 `releaseEligible` 等实际状态，不把未签名测试包标成正式可信发行。

上传前固定版本、渠道、资产清单与哈希；发布后的 tag 不移动，同版本资产不静默替换。需要修复时发布新版本。上传后的实际下载文件和云端挂载文件都要核对，不仅核对本机文件。

跨仓按 [生态跨仓契约](生态跨仓契约.md) 安排接收方与生产者顺序。插件的油猴自动更新路径也是发布入口，不能只审核 ZIP 或 Release。具体分发流程由插件仓 CONTRIBUTING.md 维护。

## 8. 本草案的落地验收

完成独立评审后，在获授权的隔离环境演练备份/恢复、迁移、worker 停入与排空、切换及回退；记录使用的实际入口和结果。尚未核实的停入能力、环境参数或权限不能由执行者猜测补齐。此次文档起草未部署、迁移、重启、发布或完成这些演练。
