# 采购任务飞书镜像 P0

更新时间：2026-08-26
状态：代码与合成测试完成；默认关闭；尚未部署，尚未写入真实飞书 Base。

## 目标与事实源

- PostgreSQL 是采购任务、认领关系和执行状态的唯一业务事实源。
- 飞书多维表格只承载团队协同镜像，不参与认领、并发控制或状态裁决。
- P0 镜像两个表：采购单主表 38 个字段、采购明细表 59 个字段；明细通过「关联采购单」指向主表。
- 同步业务键分别为 `orderKey` 和 `lineKey`，数据库同时保存飞书 `record_id`，禁止按标题、行号或列表顺序猜测记录。

## 已完成链路

1. 采购草稿保存、正式提交、认领变化、退回变化和下单执行事件继续写入事务 Outbox。
2. Worker 启动时先读取飞书字段定义，严格校验 38/59 字段集合、字段类型、单选项和明细关联目标；预检失败时不领取事件。
3. 每个事件按“主表 saving-draft → 全部有效明细 → 主表 draft-synced”顺序写入，避免主表提前显示完成。
4. 写入前按业务键精确查重；写入后按记录 ID 回读关键字段。重复业务键、数据库映射冲突、远端记录消失和字段漂移都会进入明确冲突/失败状态，不静默新建副本。
5. Worker 使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 领取事件，支持进程重启后的超时恢复、有限退避重试和新版本覆盖旧事件；重复消费不会创建重复业务键。
6. 飞书 Bitable v1 的关联字段按记录 ID 字符串数组写入，并兼容其嵌套 `record_ids` 回读结构。

## P0 字段边界

本阶段同步订单标识、店铺/站点、销售订单与收件信息、提交/草稿同步状态、认领人、认领时间、明细工作流状态及插件提交的采购指导数据。

以下字段有意不由当前投影覆盖：商品/采购/物流附件，以及「实际下单金额、采购平台订单号、物流单号」等批次执行结果。原因是一个采购明细可拆成多个正式采购批次，而当前 Base 每条明细只有一组标量执行字段，直接覆盖会造成有损聚合。现有日用结果双写继续使用其独立结果表；在确认一对多展示口径前，镜像 Worker 不清空 Base 中的人工协作内容。

## 启用闸门与回滚

启用前必须依次完成：备份共享测试 PostgreSQL、核对当前 Alembic 版本、升级到 `0012`、在全新脱敏 Base 或获准的测试表完成只读预检、再设置完整坐标并开启 Worker。首次写入只能使用全新的脱敏 `orderKey`，并人工核对主表、明细关联、认领变化和重复投递结果。

任何真实采购 Base 写入、共享测试部署或生产部署仍需当次明确授权。本轮没有把 `0013` 迁入共享测试数据库、没有启用采购 Base Worker、没有写真实采购 Base。若启用后预检失败，应先关闭功能开关并修复表结构；数据库回退只能在确认没有依赖新增列的未处理事件后执行 `downgrade 0012_buyer_account_credentials`。
