# 建环境判重与解析计划额度修复（20260916）

## 背景

20260916 测试机（xynigo.samforo.icu）运营建环境时连续被拒：截图错误是「短时解析计划过多」（HTTP 429，`environment_plan_limit`），但它只是次生故障。

实测时间线（UTC）：

| 时间 | 动作 | 结果 |
|---|---|---|
| 06:31–06:49 | 连传 5 个号商交付文件（30/20/60/59/30 行） | 每次提交都 409 `environment_account_already_bound` |
| 06:51–07:01 | 又点 5 次 | 全部 429，组织被卡约 30 分钟 |

用服务端密钥解密当时的计划并逐行比对环境清单后确认：这 5 个文件里分别只有 8、5、1、1、8 行是已建环境的账号，**绝大多数是全新行**。真正的问题是两条叠加：

1. `reserve_environment_names` 的判重**整批拒绝**，且错误里不说是哪几行，运营只能改文件重传；
2. 每次重传生成一个新的短时解析计划（30 分钟 TTL），额度按**租户**统计、上限 5，且**没有释放入口**，于是重传把全组织拖停。

当天该租户 21 次上传、8 个批次、17 次判重拦截；历史累计判重拦截 72 次，配额耗尽仅 2 次——说明运营痛点在判重，配额是放大器。

## 评审要点

1. `skipConflictingRows` 的语义：默认关闭、只在运营显式勾选后生效；裁剪是否遗漏别的按行对齐量（当前处理 `totalCount`/`progressTotal`/`verifySampleCount`/`assignments`/计划行）。
2. 取代语义：同一用户+站点+分组的旧计划被立即结束；两个标签页同时准备不同文件时，旧标签页会收到 `environment_plan_superseded`，而不是静默失效。
3. 错误响应新增 `detail.diagnostics`，与既有 `error.diagnostics` 前端契约一致；未改任何既有错误码的取值。

## 顺带发现（不属于本单，未改）

1. **生成物核对方法有版本歧义**：`CONTRIBUTING.md` 要求用 Python 3.12 跑生成器后 `git diff --exit-code`，但基线里的 `environment_plan_core.py` 是 Python 3.9 生成的——3.12 的 `ast.unparse` 会去掉 `for (a, b) in ...` 的冗余括号，因此该检查在未改动任何源码时也会报差异。本次已还原该文件，未把无关差异并入本单；需要确认生成器基准解释器（改文档或统一重生成一次）。
2. **`codex/after-sale-tracking-defaults`（0039）已核验可合并**：相对 `origin/main` 仅 1 个提交、可快进、`git merge-tree` 无冲突；把它的迁移与测试临时取入当前 main 后 `test_migration_timestamp_defaults.py` + `test_after_sale_claim.py` 全部通过。测试机数据库的 `after_sale_refund_tracking.created_at/updated_at` 已有 `now()` 默认值（手工 DDL 生效，④回访不再 500），但**新库/生产首装仍会复现 0038 漏默认值的问题**，合并前这条修复不完整。
3. 平台侧：本地/云端副本、错误码文案、`detail.diagnostics` 通道均未新增对外字段名以外的契约变化。
