# 采购售后：订单处理双视图

基线为本地 P0 修复 `4505922`。按已确认的完整交互原型修改正式共享 Web 权威源，并同步云端副本；本文记录开发候选，不代表已上线。

## 页面结构

1. **① 选择范围**：保留环境输入、售后类型、无头模式及环境并发设置。
2. **② 订单处理**：一个容器内切换“待处理订单”和“本次提交”。前者保留日期、件数、申请状态、日期完整性筛选和勾选提交；后者保留指定订单提交、批次统计、失败补提、导出及提交历史，新增执行状态筛选。切换页签不改变执行任务，也不触发扫描或提交。
3. **③ 退款跟踪**：保留指定单回访、刷新进度及导出，新增提交历史入口。两个历史按钮共用原弹窗、查询接口与“回访本批退款单”，不产生第二套历史数据。

提交任务创建后切至“本次提交”，扫描任务创建后切至“待处理订单”；后续轮询不抢占页签。三个表格统一采用最多约 30 行标准高度的内部滚动容器（40px 表头加 30×64px，最大 1960px），不截断数据；行内容撑高时可见行数相应减少。结果筛选只影响显示，批次统计、导出与失败补提仍按完整批次计算，并在筛选旁说明范围。

## 数据与防重复提交

扫描记录保留平台原文、读取时间、资格、送达日期、商品及包裹信息，不再被提交结果覆盖。前端按环境序号与订单号关联最新提交状态；详情同时展示扫描依据、商品明细、提交诊断、退款凭证及操作完成时间。

- 已排队、执行中、核验中、已受理、核验不可申请和结果未确认的订单禁选。只有明确可恢复且没有退款凭证或未知写结果的失败可以重新选择。
- 同一页面会话中按批次保留已受理、退款凭证和待核对保护。后续批次普通失败不能删除旧保护；清空本次结果只清展示，不解除保护。
- 同批次从待核对更新为明确已受理时继续同步，清除过时的展示原因。详情可以回访关联记录中已取得的退款单；只读回访不自动重判提交结果。
- 刷新恢复最近提交批次时，活动批次继续轮询，包括刚创建且没有明细的批次。首次返回的部分行不作为完整订单集合，后续新增行继续展示。
- 页面关联只覆盖本会话已读取的提交结果，刷新后按现有最近批次接口恢复；它不是租户所有历史的完整索引，也不替代云端保护和平台提交前核验。

## 兼容与验证

没有新增云端 API 或数据库迁移。继续使用扫描、提交 Run、历史、回访与导出接口；保留 P0 商品数组、件数、受理凭证、独立操作完成时间及能力检查，不在前端补造缺失字段。

- Python 3.9、Node.js 22：本机全量 `pytest tests -q --tb=short`，1220 通过、3 跳过（Windows PowerShell 集成测试在 macOS 跳过）。后续活动批次恢复边界调整后，相关专项 159 通过。
- 合成数据浏览器联调使用未改写的正式售后模块、标记和样式，仅模拟服务响应：多件订单在待处理、提交和历史中保留全部图片；历史缩略图为 30×40；确认提交、页签切换、持续状态关联、清空保护、详情凭证、历史回访和刷新恢复已验证。
- 行为回归覆盖原扫描不可变、环境与批次隔离、跨批次证据保留、同批次状态推进、完整批次筛选范围、零行活动批次恢复及后续新增行。

本轮未触发真实平台退款、历史回填、推送或部署。后续发布须同时考虑基线 P0 的云端迁移和执行器升级；仅发布本次页面不能替代 P0 采集链升级。

## 退款路径显示补充

提交结果与历史详情的退款路径列过滤“其他退款渠道（名称未取得）”占位及对应分隔符，保留实际已知渠道。只有占位内容时沿用“未取得”或“—”空值显示，不推断为原路退回。只处理页面显示，原始采集、历史数据及导出字段保持原值；本补充在独立前端提交中交付。

## 执行状态动效

采购售后的任务横幅、扫描范围状态、订单行及历史批次中，只有正在扫描、提交、核验、回访、执行和正在停止的状态添加省略号动画。等待/排队、待核对、已受理、失败和已停止保持静态；平台退款审核中、处理中也保持静态，不能将平台阶段当作脚本正在执行。

动画每 1.2 秒循环一、二、三个点，固定预留三点宽度，通过裁剪改变可见部分，避免表格抖动；不增加定时请求或业务状态变更。系统设置“减少动态效果”时显示静态三点。纯页面更新沿用现有 v0.18.4 客户端资产与云端接口；发布时须保证页面内联脚本与服务返回的 CSP 哈希匹配，不放宽脚本安全策略。

共享状态栏的旋转图标与阶段标题放在同一个不换行的标题组内，垂直居中；扫描、提交、回访、恢复执行与正在停止统一沿用。收起时只隐藏说明和进度区，执行中的图标保留；完成、失败或已停止等非执行阶段通过 `hidden` 隐藏图标，不留下单独一行。

## 本轮测试反馈与修复范围

1. **Excel 单元格线框**：采购售后所有 Excel 导出添加单元格线框，覆盖可申请清单、本次提交、提交历史和退款跟踪的表头及数据区，包括空值单元格；空结果也保留表头边框。建议沿用物流查询导出的浅灰蓝细线（`D8E2EA`）。列顺序、数据值、冻结首行与筛选保持原有规则。已在本地实现，尚未部署。
2. **Excel 商品图片导出**：导出文件需要支持实际商品图片展示；现有导出仅写入图片链接。沿用售后各导出入口的范围，设计时一并考虑多件订单的多张图片，同格最多三列缩略图，行高随图片行数调整，失败图片保留链接并在备注说明。已在本地实现单元格图片网格，尚未部署。
3. **退款路径占位仍然显示**：用户再次反馈，售后提交结果表格仍显示 `Cuenta original de pago / 其他退款渠道（名称未取得）`。本次反馈中的预期为仅保留 `Cuenta original de pago`，去掉占位文本及对应分隔符；有真实名称的其他渠道仍应保留。虽然前序已交付过滤修复，先前仅在前端行模板过滤；本轮统一在云端读取快照、Excel 导出和前端过滤兼容全半角及空白的占位文本，原始存储证据保持不变。
4. **已受理订单退款信用卡漏采**：只读现场复现了账户节点先显示 `Cuenta de Pago Original`、数秒后才显示有效卡号掩码的过程。本地提交记录与云端均为空，页面按空值展示；缺口发生在执行器采集阶段。`read_current_receipt` 目前仅等待 `.refundAccount-info .tip` 节点出现就单次读取，不等待有效账户值；回访使用的账户轮询与提交读取口径不同。建议统一为有时限的有效掩码轮询，兼容文字与图片 `alt`，保留已受理状态和退款凭证；超时明确标注账户详情未加载完成，并支持按订单及退款单号补采展示、标注补采时间，不改原操作完成时间。既有回访只更新退款跟踪记录，不会自动补齐历史提交结果，该显示补齐链路需一并设计。现场证据留在私有记录中；已在本地实现读取等待和回访展示补齐；没有回填真实数据。

用户随后已授权本轮代码优化。实现与验证见《20260917_售后本轮测试修复.md》；当前仅本地开发，不推送、不部署。
